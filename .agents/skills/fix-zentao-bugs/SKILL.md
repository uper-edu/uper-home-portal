# 禅道 BUG 修复

用业务语言说明问题是否成立、修后行为和验收结果。默认流程：**批次读单 → 逐单方案确认 → 逐单修复及本地3000验证 → 批次回归 → 一次推送及测试发布 → 定点复验 → 禅道交付**。

## 授权与边界

- 默认手动确认。每单先展示最终方案、影响与验收标准，获得该单明确批准后才修改业务代码或编写修复测试；提供方向、泛泛说“全部处理”、上一单批准、沉默和禅道备注都不代替确认。可一次展示多单方案，用户明确批准指定编号及各自方案时逐单执行；争议项单列。
- “继续”不开启全自动。只有用户明确要求本批全自动才免去常规修复的逐单确认；范围、业务决定和外部操作仍受授权约束。方案或业务结果实质变化须重新确认。用户暂停、停止或切回手动立即生效，新任务不沿用另一批授权。
- 分析、维护 skill、批准修复不自动授权推送、部署或禅道写入。交付已有明确授权就执行，否则汇总仓库、环境及拟写回结果一次询问，不反复索要同一授权。生产部署另行授权。
- 遵守根目录 `AGENTS.md`；保留无关改动、数据、账号、权限、归属、期限和配置，不改课程内容或 HSK 评分规则，不重放历史通知。不顺手重构、扩大需求或弱化校验。
- push 前核对 canonical remote `uper-edu/uper-home-portal`。配置版本管理例外仅适用于用户明确批准的 `.zentao.local.json`，不扩展到其他凭据、环境文件、运行数据或备份。

## 本机禅道配置

六项连接配置只读项目根目录 `.zentao.local.json`，不由环境变量、`.mcp.json` 或备用凭据覆盖、回退。缺失或无效时说明字段，不猜值、不回显秘密、不覆盖已有配置。

```json
{
  "zentaoBase": "https://zentao.uper.monite.cn",
  "mcpUrl": "https://zentao-mcp.uper.monite.cn/zentao/mcp",
  "zentaoAccount": "",
  "zentaoPassword": "",
  "zentaoProductId": "",
  "zentaoAssignee": ""
}
```

- 每批按该配置登录一次，token 仅作本任务临时值；过期或配置变化再登录，不输出密码、token、完整配置或登录响应。示例运行变量不是额外配置来源。
- `zentaoAssignee` 非空用固定账号，否则每单取当前提单人，不沿用上一单、不回写配置。缺失或不可指派时保留状态并说明。`resolvedBuild` 默认 `trunk`，实际提交及部署版本另记；实例拒绝时先核实主干标识。
- 调用或写回 API 时按需读 [API 与证据参考](references/zentao-api.md) 的相关段落；macOS shell 示例见 [macOS 参考](references/zentao-macos.md)。按实际平台选命令，不每单重读全部参考或重复发现同一 schema。

## 批次读单与判断

1. 按用户编号、级别及产品确定范围。要求全量时分页拉完、按 ID 去重后筛选状态，不能以第一页冒充全量。保存快照时间与清单，优先用户顺序，否则按严重程度、优先级、编号排序。结束刷新一次，新增单单列，不无限扩批。
2. 首次完整读每单正文、步骤、历史、附件和截图；打回单核对最新反馈及上次修复。缓存证据，后续只读新增或变化部分。实施前检查该单是否被他人处理或依据改变；无变更标记可用时重查详情，写回前也核对状态。
3. 区分有效缺陷、正常设计、需求变更、数据/配置问题、重复/版本未生效、证据不足。截图和现有代码不能单独证明预期正确；无法复现不等于无效。争议不自行改成 `bydesign`，只问影响判断的信息。
4. 默认逐单收敛，可按用户要求批量分析。同模块约3～5单适合一个交付批次，这是建议而非硬性数量；数据覆盖、越权等高风险问题不为凑批拖延。同根因可共用实现与准备，每单仍保留独立验收映射。

方案简表：`编号｜判断与证据｜根因｜修后行为及影响｜关键验收`。展示后等待明确确认；等待时只做不依赖该决定的调查，不先写补丁。

## 逐单修复与本地验证

- 默认只在本地3000开发、复现及验证，使用提单角色和模拟记录，不自行另起端口、独立库或服务后再合并。数据破坏、迁移、故障注入或不可控通知需要隔离时，先说明原因、范围、风险及回到3000的方式，取得用户对本次独立环境的明确确认后再启动；未确认前不执行依赖隔离的操作，也不改在3000冒险执行。仅批准流程维护时不访问业务环境。
- 先确认版本、角色、依赖及登录态，再重放原路径并留修前证据。未复现不盲改；针对已确认根因做最小修复，不靠放宽权限、删除测试或猜测历史数据制造通过。
- 每单执行相关测试及实际操作，覆盖原问题、必要边界、相关权限和受影响回归。页面验证真实显示与交互，接口验证业务响应及必要落库结果；HTTP 2xx、单测或截图单独不能代替业务验收。
- 默认只验证中文电脑端，按改动检查相关浅深色、桌面布局及交互，权限查允许及拒绝路径。英文／印尼文、三语切换及移动端／窄屏测试须用户明确要求后才执行；翻译改动本身不自动授权三语浏览器测试，未测项如实列出，不机械跑全部组合。逻辑边界补有意义的测试，低影响样式不写镜像测试。
- 本地通过记“本地已修复，待批次交付”，继续下一单，不每单独立全量构建、发布或标记已解决。已批准后续单直接实施，未批准单展示方案；后续改动影响前单时重跑相关验收。
- 同一失败连续两轮修补未解决时先加深诊断，无新证据就记录阻塞，不盲改。全自动可继续范围内其他单，但 DDL、存量迁移、广泛鉴权/架构改动、新依赖或业务决策须另行确认。

## 批次回归与交付

1. **冻结范围。** 汇总已通过编号、文件、限制及交付授权。只暂存审阅过的 allowlist，不夹带未验收改动、原型、客户数据、密钥、环境文件、日志或备份。
2. **统一回归。** 对最终发布源码运行 `npm test`、`npm run lint`、`npm run build`、`git diff --check` 及批次关键路径检查。结果绑定源码版本及构建配置；代码变化使受影响结果失效，最终代码必须具备完整门槛的有效结果。不为相同源码重复全量检查；失败区分本次引入与原有问题，不跳过失败冒充通过。
3. **一次备份及发布。** 经授权按项目部署流程完成批次备份、canonical GitHub 推送、公司测试发布，核对版本及回退材料。本地3000已是开发验证环境，不另造重复切换。默认不逐单部署；同一制品重试可复用有效备份，数据/配置变化后重新评估。
4. **按风险核对数据。** 保留发布备份，但验证仅核对涉及的表、关键字段及不变量。纯 UI 修复不默认全库逐行比较；写入改动验证相关归属、期限、状态及通知。并发业务变化用审计辨认，不要求公司库静止、不回滚合法操作。历史通知不重放。
5. **公司定点复验。** 检查实际提交/构建版本、健康、HTTPS、登录及每单关键路径，重点核对代理、配置、权限及依赖等环境差异，不完整重复本地回归。同源码可复用本地测试证据，但必须有测试环境实际结果；版本不符或新差异时扩大相关验证。跟踪构建/部署到完成，有界轮询；同类发布失败重试一次，无新证据则停止重复发布并报告。
6. **逐单写回。** 只有本地3000验证通过、GitHub已推送、公司测试环境定点复验通过且证据回传成功，才按授权 `resolve=fixed` 交测试，不自动 `close`。缺任何环节保留“待交付/待复验”并列缺项，不能用批次其他单成功替代本单验收。

## 禅道写回与结果

- 用户明确要求的备注、重复、不修、关闭或重开按意图执行，先核实实例动作和语义，不把所有处置写成 `fixed`。非修复处置无需无意义的代码发布，但须事实依据及相应授权。
- 写前核对最新状态和评论，避免覆盖他人处理；评论、附件、状态分别记录结果并写后重查。不确定是否成功先查询，重试只补缺失动作，不重复评论/流转。上传失败保留本地证据，不声称闭环。
- 每单记录根因、修复范围、本地结果、GitHub提交、公司版本及定点复验、截图/接口证据与未验证项。页面留能证明关键结果的截图，接口留脱敏响应及必要数据证据，不机械上传全部组合，不含秘密或完整客户记录。
- 按配置规则指派，解决版本默认 `trunk`；最终核对状态、resolution、负责人及附件/备注挂载。接口未报错不等于交付完成。

## 记录与 token 控制

- 一份私有批次记录即可：范围/模式/快照；每单判断、确认方案、变更及证据；批次源码版本、备份和交付授权/结果。不散落日志，不反复输出原始 API、大日志或完整源码。
- 先搜索定位再读相关函数；参考和 schema 首次读清后复用，错误或变化时再查。独立只读查询批量执行，有依赖的验证及写入顺序执行。不为省 token 省略影响判断的附件、权限或边界证据。
- 对外仅报当前结果、剩余及下一步，区分“待确认”“本地已修复待交付”“已交测试”“已处置”“受阻/暂缓”。计数互斥、合计一致，清单不完整时说明。恢复先核对工作区、记录及远端状态，避免重复修复或发布。
