## 1. 目标、边界与建议结论

销售应能回答：现在先做哪项任务、它来自哪件事、是否已有相关安排、处理后还有哪些事。任务不能因为新消息到来而被悄悄覆盖，也不能每来一条消息就新增一次联系任务。

建议统一五条规则：

1. 同一请求重复提交，不新增任务或重复依据。
2. 同一件事有新信息，补充原任务；只改时间，明确改期。
3. 不同的事可以并存；同一类型不代表同一件事。
4. 原工作确实不再需要时，才明确取消或替代；替代不是完成，也不是清除逾期历史。
5. 只完成选中的任务；新任务不自动完成、改期或删除旧任务。

保留账号、权限、客户归属、历史任务及原截止时间、运营时区、通知策略和HSK规则。不自动合并Lead，不重新分类，不设计Offer推荐算法，不建立独立暂停状态。本轮文档不授权开发、迁移、推送GitHub、公司发布或禅道写入。

| 通知 | 任务事件、通知版本、取消关联待发通知等已有链路 | 补充与改期对任务展示、排序和通知的影响需统一；不得借整理任务补发旧通知 |

## 3. 业务概念：类型、事情与时间分开

| 名称 | 含义与例子 | 不代表什么 |
|---|---|---|
| 任务类型（Task type） | 顾问联系、确认预约、跟进报名、普通跟进、内部复查等工作类别 | 两条预约任务不一定是重复 |
| 具体事项（Business matter） | “确认本周六试听A场次”或“处理本次课程报名咨询” | 不是客户姓名、活动码或一句相似文字 |
| 来源依据（Source evidence） | 对话／消息、请求事件、人工记录；保留原文、来源ID及时间 | 新消息不一定是新任务，也不等于已人工回复 |
| 原截止时间（Original deadline） | 当时承诺或策略产生的处理期限，保留来源和规则快照 | 不因重新安排、分组变化或Owner变化而覆盖 |
| 当前安排时间（Scheduled time） | 员工明确安排的执行／预约／复查时间 | 未来安排不能消除已经发生的逾期 |
| 当前处理条件 | 身份、归属、联系约定等决定现在允许做什么 | 不能据此把任务自动标完成 |

一项任务描述一个可明确完成的工作。任务可关联多条依据；同一条客户消息确实包含不同请求时，可关联不同事项的任务，去重键必须包含请求类型／事项，不能只用消息ID。

## 4. 新增、补充、改期、替代与并存

### 4.1 判断顺序与操作结果

| 顺序／情形 | 建议处理 | 任务数与期限影响 |
|---|---|---|
| 同一来源、同一请求的重试／重复点击 | 返回原保存结果，不重复追加依据 | 新增0项；原任务保持原状，包括已完成／已取消状态 |
| 已明确关联同一事项，原任务仍未完成，新信息不改变原工作 | 补充依据（Supplement） | 新增0项；不改归属、状态、期限或联系约定 |
| 同一事项，只调整执行时间 | 明确改期（Reschedule），预览原期限与新安排，填写原因 | 新增0项；原期限保留，写新安排及历史；不自动顺延响应SLA |
| 同一事项，但原工作已不再适用，需要另一项工作接替 | 明确替代（Replace），指定旧任务并说明原因 | 新增1项、旧任务取消；双向关联，不能标旧任务已完成 |
| 不同事项，或原任务已结束后出现真正的新请求 | 新增（Create），保留来源与业务关系 | 新增1项，和其他未完成任务并存；新期限按现有策略或明确人工安排确定 |
| 不能确定是不是同一事项 | 展示可能相关任务，由有权员工选择；自动入口先保存新依据并标待确认归属 | 不自动合并、取消或改期；避免丢请求或反复新增同类任务，详见4.2 |
| 客户只增加普通背景信息，没有明确请求或人工安排 | 保存对话／资料，必要时作为已关联事项的补充 | 不因每条消息、活动归因或测评完成自动造跟进任务 |

“补充”不能藏着修改任务动作、负责人或期限；确需修改时走相应显式操作。澄清任务描述可作为明确的描述修订，保留前后值，不改变事项、状态或期限。普通联系保存成功、联系接通或阶段变化均不自动结束其他任务。

### 4.2 不能自动确定关联时，既不吞请求，也不制造任务堆积

推荐采用以下保守规则，作为需要确认的业务选择：

- 可靠关联来自已保存事项ID、明确选中的任务、已有预约／申请标识；不以手机号、任务类型或文字相似度自动判为同一件事。不新增AI语义决策。
- 自动入口没有可靠关联、也没有同类开放任务时，按现有请求类型创建任务，并建立该次事项关系。
- 有同类开放任务但无法确定关联时，保留独立的“请求待确认关联”依据，进入有权限员工的处理列表；显示“新请求待确认”，不无声挂在旧任务下，也不自动取消原任务。系统维护可查询的依据处理状态及首次收到时间。
- 待确认依据不另造一套普通任务。任务工作区展示它，并提供“补充这项任务／另建任务”两项明确操作。即使原任务后来完成，它仍须可见，不随旧任务消失。
- 新请求的响应期限从实际接收时刻按原请求策略计算；处理关联不重新起算。到期前必须可见、可按原策略提醒。关联原任务后保留原任务期限，同时展示该新请求尚未处理的期限；完成任务必须明确覆盖哪些未处理请求，不能把新依据自动算作已答复。
- 如果这一依据处理和期限链路暂不能完整实现，就不能只改成“停止按同类复用”，否则会漏跟；该链路是实施门槛，不是可省略的界面细节。

该设计增加的是“来源是否已归入工作”的审计信息，不增加客户业务状态，也不要求销售逐条分类所有普通聊天。

### 4.3 替代与取消的限制

替代必须在同一Lead中明确选择旧任务，展示“取消什么、建立什么、哪些保持不变”。不同事项不得默认替代，只能并存；确实需要撤销旧事项时，分别记录取消依据和新事项。

旧任务、原期限、逾期事实、原消息保持不变。新任务记录自己的期限、替代关系及旧事项的原期限引用；不能把旧逾期变成“从未逾期”。仅改时间优先使用改期，不用替代重置SLA。已完成、已取消或历史待确认任务不可被静默替代／重新打开。

单独取消需原因，不等于已完成。结束唯一有效安排后，不能再声称“保留已有安排”；可按现有规则安排下一步或仅保存真实事实，并明确提示尚无后续安排。

### 4.4 复查任务沿用P0，不与普通任务混淆

复查任务用于内部复查。普通未来任务不限制联系；只有明确的日期约定才限制提前外联。修改复查约定沿用P0：保留旧记录，只取消关联旧复查并建立新安排，不顺带取消普通任务。全体业务任务可以并存，但同一当前联系约定只能有一个生效版本，不能并存两个互相矛盾的外联日期限制。

到日期只结束相应日期限制，不自动完成复查、不发消息，不解除身份或停止联系限制。停止联系时仍保留业务任务及原期限，转为内部核实／处理。

## 5. 优先级：先判断能做什么，再决定先做哪件事

### 5.1 不改变客户列表现有逻辑

身份待核实Lead继续在原筛选及权限范围内置顶；不强行进入用户筛选排除的集合。保留客户列表的角色默认、个人排序、分类规则和Owner范围。任务排序不重算Tier，不改客户SLA或已有任务期限。

### 5.2 同一客户和跨客户任务视图共用规则

建议任务工作队列按以下次序排列：

1. 有效期限已逾期的事项。
2. 运营时区今天到期的事项。
3. 未完成的明确顾问／预约／报名请求，包括尚待确认关联的新请求。
4. 其他有效任务／到期内部复查。
5. 缺期限、历史待确认及缺少后续安排等需核实项；真实紧急请求缺时间时明确提示，不伪装成普通远期任务。

同组按尚未处理事项的最早有效期限、可靠来源时间、稳定ID排序。没有可靠时间不能补造；日期异常单独提示。未来普通任务保留可查，不混入默认“现在需处理”集合；已完成／取消默认折叠。

这是**拟统一的任务工作队列规则**；现有单客按截止时间排序与现有客户排序并非完全相同，实现时需分别测试，不能宣称现在已经一致。原客户列表非“处理优先级”排序保持用户选择。

身份未核实、尚无Owner、停止联系或有效日期约定不会消除逾期：卡片显示原期限及受限原因，主操作改为核实、分配／认领、内部处理或复查。普通销售不可执行的操作不变成可点击的联系按钮；管理者也不能绕过停止联系限制。不要用Hot分组替代任务优先级，也不新增可随意把逾期挪到底部的人工优先级。

## 6. 任务中心与Follow-up：两层工作区，共用一套任务

### 6.1 专业建议：需要统一工作入口，但不是把所有内容塞进Follow-up

客户列表以人为单位，适合判断背景及归属；任务中心以工作为单位，适合跨客户处理期限与请求；Follow-up是某位客户的处理工作台。三者共用任务、依据、权限和保存事务，不分别维护“下一步”。

建议在销售线索现有工具栏增加“客户／任务”视图切换，先不增加顶层模块或新的全局筛选区。任务视图承载任务中心能力。Sales默认本人需处理，Manager默认现有授权范围；保留全部查看和既有筛选。任务视图可同一客户多行，数量明确叫“待处理事项”，不冒充Lead数。一个任务有多条待答请求时，同一卡片列出数量与最早期限，展开处理，避免重复任务行。

每行稳定展示：客户与Owner、具体动作／事项、依据摘要、原截止时间与当前安排、限制原因、主要操作。缺少关联的请求和缺少后续安排是明确标识的待处理项，不能伪装成已经存在的任务。

### 6.2 Follow-up承担单客闭环

按以下顺序集中展示：

1. 当前可处理动作和限制原因；多任务数量及最早期限。
2. 开放任务／待关联请求：动作、依据、负责人、原期限、安排时间；一个主要操作，补充／改期／替代／取消放次级菜单。
3. 上次人工联系原文及独立客户备注。
4. 当前任务的处理表单，明确将完成哪些任务、哪些请求已处理、下一步保留或新增什么。
5. 已完成／取消及任务变更历史，按需展开。

从任务视图直接打开该客户并聚焦对应任务；从客户入口进入不默认完成任何任务。从某任务入口进入仅预选该任务，员工仍须确认完成。跨任务处理需显式选择并逐项核对，不把一次接通等同于全部解决。

使用现有稳定操作层，不向页面中途插入大表单造成跳动。保存后就地显示实际新增、补充、完成、取消及保留项；失败、超时、并发冲突保留草稿，支持查询原保存结果，不自动跳下一位。返回保留任务筛选和位置，已失去权限的客户不能凭旧行进入。

### 6.3 分步交付，避免入口先行、规则仍散

- **A：规则和单客闭环。** 先统一所有任务入口及Follow-up，复用P0规则；未关联新请求必须在现有工作列表和单客Follow-up可见。相关验收通过后才进行B。
- **B（backlog，本轮不实施）：跨客户任务视图。** 在同一规则及数据上增加任务中心视图、筛选与数量；不复制任务数据，不另开一套通知。

已批准只实施A，先把单客Follow-up做完整；B保留为需求backlog，待A优化后重新评估、另行批准。不新增客户／任务视图切换或跨客户任务入口。

## 7. 角色、事务、通知与数据保护

### 7.1 权限与并发

沿用现有客户读写、任务处理、分配及三项配置权限。任务可见不新增客户访问权限；系统管理员身份不自动获得CRM权限。默认任务负责人继承客户Owner；本方案不新增Sales自由把任务分给他人的能力。既有不同任务负责人保留并明确显示，不强制回填Owner。

每次保存重新校验Lead、目标任务、来源、当前Owner／权限、版本与联系限制。管理者普通协助自动留痕，不另要求通用“代处理申请”；改期、替代、取消仍需对应业务原因。任务取消与联系授权是不同操作，不把“不能外联”误解为所有内部处理都禁止。

同一事务写入选定变更、依据关联、处理记录、审计及必要通知事件；失败全部回滚。保存编号带客户和操作范围，相同编号同内容返回原结果，不同内容拒绝混用。并发创建同一请求只有一个结果；两人同时修改同一任务，后一人收到可读冲突并保留草稿，不覆盖新安排。任务已完成后重试旧请求也不重新建任务；真正新消息的新事项可以建立新任务。

### 7.2 通知不增设策略、不补发历史

- 新任务、新请求待确认、显式改期按现有事件策略和频控处理；若当前策略不支持某类依据提醒，须给出明确策略映射，经确认实施，不能悄悄打开新规则。
- 补充普通背景或重复来源不重复通知；新的明确请求仍按原策略保留提醒资格，不因挂到旧任务而被吞掉。
- 完成／取消／替代只取消关联的待发通知。通知在发送前重新检查任务、版本、归属及联系安排；已被外部接口接受不标撤回，结果未知不盲目重发。
- Owner→CRM Manager路由保持；内部复查与对客联系在卡片中区分。不改变其他任务期限、条件、时间、频控和渠道。
- 老事件、旧失败或新版本上线不自动重放。所有故障验证采用模拟发送或隔离环境，不向真实群制造故障。

### 7.3 最小数据与接口扩展方向（待实施）

复用现有任务命令及跟进保存接口，统一调用一套任务规则；不是让前端自行猜测后选择不同数据库写法。保留现有任务ID、种类、状态、Owner、原期限和版本。

必要扩展包括：具体事项标识；来源请求及幂等唯一关系；待确认关联／已关联及处理结果；新请求原期限；任务替代双向关系；描述／时间修订审计。具体事项标识由可靠业务记录或明确人工选择建立，不能用自由文本哈希冒充稳定业务关系。技术存储表及索引在批准后的实现设计中定稿，必须支持事务、唯一性、权限查询及恢复，不只存一个无法校验的提示字符串。

现有任务没有事项标识时保留原样，不批量猜测、合并或补造承诺。首次显式处理时可确认关联；原截止缺失明确显示未记录，不用当前时间补齐。新接口需返回实际任务和依据变更清单，旧请求若缺少必要选择应返回可读错误并保留输入，不能恢复危险的按同类自动覆盖。

## 8. 具体业务实例

**实例一：多个明确请求并存。** 客户已有“周六试听确认”，又提出课程报名问题。没有可靠依据说明是同一件事，分别保留预约和报名事项；先按实际期限处理。一通电话只解决试听时，仅完成试听确认任务，报名任务保持原期限。

**实例二：同一预约补信息与改期。** 已关联预约A的客户补充“希望带朋友”，补充原任务依据；随后明确将A改到下周，员工确认新时间和原因后改期。原期限仍可见，不把改期说成已完成试听。另约预约B则新建另一事项，不因都是booking而吞并。

**实例三：原工作不再需要。** 原任务是准备线下到访材料，客户明确改为线上咨询，员工确认原材料工作取消并用线上咨询任务接替；保留原任务、原因、原期限及新任务关系。旧任务已逾期的事实不因替代消失。

**实例四：再次点“请顾问联系”。** 同一提交重试十次只产生一次依据。不同新消息无法确定是否同一次诉求时，显示待确认新请求和原接收期限；员工明确补充旧事项或另建，不延迟到旧任务完成后才发现新请求。

**实例五：约定日期前又收到客户提问。** 仍保存新消息和请求，不能自动清除日期约定或结束原复查。员工按P0回复用途检查处理本次新询问；原预约及复查安排保留，除非明确修改。阅读或打开WhatsApp不算已答复。
