## 1. 已实现范围

- 单客Follow-up按当前任务／新请求、沟通依据、历史组织。任务数量和主要操作集中在紧凑固定工具栏；原话及补充按需展开，次要操作使用已有操作层，不在页面中插入大表单。
- 明确请求按客户、会话、消息及请求类型识别重复。同来源重试不重复保存；不再仅凭类型相同自动关联。已有同类开放任务时，新请求保留为待确认依据，员工明确补充或另建任务，保留收到时确定的响应期限。
- 新增、补充、改期、替代和取消共用服务端规则，已接入独立任务菜单及跟进保存。普通新事项与原任务并存须确认；补充内容保存在原任务；改期不覆盖原期限；替代须确认同一事项，取消原工作并保留关联历史。
- 新请求可以先部分处理而保留任务；完成任务须明确确认尚未处理的关联请求。只影响指定任务及相关待发通知，不自动结束其他任务。取消仍有关联未处理请求的任务会被拦截，避免吞掉请求。
- 任务按逾期、今天到期、明确请求、其他任务及待核实项组织。关联请求的较早期限参与处理顺序和展示，不覆盖已保存任务期限，不重算Tier。客户原筛选、权限及非优先级排序保留。
- 待确认／关联请求复用现有请求事件和通知策略；发送前复查请求状态。已处理请求的待发通知可取消，接口接受或结果未知不伪装撤回；不启用新策略或重放旧事件。
- 联系、身份、Owner、停止及明确日期约定继续复用P0。复查约定须走联系安排，普通任务菜单不能绕过。客户原文、人工备注及HSK评分保持。
- 英文、印尼文、中文界面、校验及相关在线图文说明同步；客户级任务引用可反映关联请求和当前任务结果。

## 4. 数据与接口说明

复用`followup_tasks`、`crm_engagements`、`crm_facts`、`crm_operations`及既有Outbox；**本次没有DDL迁移或旧数据批量写回**。

- `crm_engagements.kind=task_request`保存请求、原响应期限、来源及回执；`pending／linked／handled`分别表示尚未关联、已关联但未确认处理、已明确处理。这些是请求处理记录，不是Lead新增业务状态。
- 请求ID由客户／会话／消息／请求类型稳定生成。任务`details.matterId`、补充原文、替代关系、旧事项期限引用只在明确新操作时写入；不从旧自由文本猜测事项关系。
- `/api/crm/leads/:id/trust`增加请求依据及有效请求期限。任务操作新增请求关联／另建命令，保留请求和任务版本校验。
- `/logs`增加明确已处理请求和下一步与原任务的关系，仍使用原事务、保存编号及授权；任务完成和请求处理是独立、明确的选择。记录事实不自动标消息已答复或完成所有任务。
- 已读与轻量动态检查继续分开；请求关联／处理及任务改期版本变化会使轻量游标变化，不泄露授权范围外客户数据。
