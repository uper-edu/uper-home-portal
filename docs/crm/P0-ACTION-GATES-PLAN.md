## 本轮讨论收口：销售只需遵守以下规则

1. 用任务说明“做什么、何时做”。不另设暂停状态；只有明确约定某日前不主动联系时，才在复查任务中设置该限制。停止主动联系单独保留。
2. 没回复不自动等于暂停。现有未回复处理规则、客户分组和原任务期限各自保留。
3. 管理者已有联系权限，就从普通联系入口协助跟进。不另设“代处理”按钮、事前审批或普通协助原因必填；操作后按通常流程记录实际沟通结果。
4. 协助一次不改变客户负责人。系统自动记录操作人、时间、客户及当时负责人；真正转交客户要另行明确修改负责人。
5. 权限及客户限制仍由系统检查。明确约定不主动联系的期限内不进行普通营销；停止主动联系须先恢复；身份待核实先核实。管理者不能凭角色绕过限制。
6. 只在改变联系限制、判断身份或使用身份核实／约定期间回复这类特殊入口时，填写对应的原因或依据。无需另一名管理者逐次审批。

本轮已实现以下规则；不代表其他状态拆分、同人历史汇总及分类算法也已实施。

## 1. 要解决什么问题，哪些保持不变

同一个客户，无论从列表、详情、身份比较页还是交接页面操作，都应得到一致答案：谁可以处理，现在能不能联系，不能时应该先做什么。

本轮统一身份核实、认领、负责人分配和转交、恢复联系，以及电话、WhatsApp和复制联系内容的使用条件。

现有账号、角色、客户访问范围、负责人、客户分组、销售阶段、HSK评分、任务期限和通知策略保持不变。不自动合并客户，不补改历史记录，不补发历史通知。同人历史汇总、身份判断撤销、试听记录拆分、营销方案推荐和多任务重整仍是后续项目。

客户姓名、消息和人工备注保持原文。实施时系统按钮、提示、错误和在线指南同步英文、印尼文、中文。

### 常用说法

| 说法 | 业务含义 |
|---|---|
| 身份待核实 | 两条记录可能有关联，员工尚未确认是同一人、不同人，还是共用联系方式 |
| 共享池／未分配客户 | 还没有负责人，符合条件的销售可以认领，或由有权限的员工分配 |
| 正常跟进 | 根据现有任务和期限联系客户 |
| 复查任务 | 明确何时复查什么；有客户约定时可注明“此前不主动联系”，普通未来任务不自带此限制 |
| 停止主动联系 | 不再主动联系，原因必填，不强制设置复查时间；恢复前明确说明原因 |
| 恢复联系 | 将安排改回正常跟进；身份、负责人及权限仍须分别满足 |
| 联系入口操作记录 | 记录员工获准打开电话、WhatsApp或复制内容；不证明已发送、已接通或已完成任务 |

## 2. 现在已经有的功能，还缺什么

下表保留修前缺口与本轮实施内容的对照；实际测试范围以验收报告为准。

| 领域 | 修前情况 | 本轮补齐 |
|---|---|---|
| 核实身份 | 有效且非空电话或邮箱相同会提示核实；保存判断需权限及依据 | 所有相关操作都检查最新核实情况 |
| 认领 | 已有负责人或仍需核实身份时不能认领；多人同时认领只能一人成功 | 保持规则，各入口说明一致 |
| 分配及交接 | 检查分配权限、接收人员资格和配置 | 身份未核实前，也不能分配或转交给新负责人 |
| 联系客户 | 电话、WhatsApp和复制内容共用检查；停止联系时禁止操作 | 明确约定的期限内不进行普通主动联系 |
| 管理者协助跟进 | 修前普通协助要求先填写原因，并记录当时负责人及核实情况 | 取消普通协助的事前原因必填；直接使用普通联系入口，系统自动记录，不另设审批或流程 |
| 恢复联系 | 已有联系安排、原因及复查记录 | 恢复时检查后续安排，不要求编造一次通话才能恢复 |
| 保存结果查询 | 保存超时后可查询是否成功 | 之前获准不表示现在仍可联系；实际打开工具前再次检查 |

## 3. 谁可以操作，三个配置如何保留

员工只能处理原本有权查看和跟进的客户。CRM管理者不自动获得其他客户资料；仅有系统管理员身份，也不能直接处理CRM客户。兼任管理者和销售，保留原资格，但不能绕过限制。

| 配置 | 默认值不变 | 业务解释 |
|---|---|---|
| 身份核实仅限CRM Manager | 开启 | 关闭后，销售只有原本就能查看并跟进双方记录，才可以判断身份；不会获得其他客户资料 |
| Lead分配Owner仅限CRM Manager | 关闭 | 开启后认领、分配、交接还要求管理者身份；关闭时沿用原有权限，普通销售不因此获得分配他人客户的能力 |
| 待核实来源归因仅限CRM Manager | 开启 | 保留现有来源核实规则。活动来源未核实，不等于客户身份未核实 |

关闭配置只解除对应的额外角色限制，不增加原权限。允许销售判断身份，不代表允许销售在核实前联系客户；需要联系才能核实的，仍由有权限的管理者处理。

## 4. 各种情况下可以做什么

先检查账号及资料访问权限，再检查配置、身份、联系安排、负责人、操作用途和必要依据，最后确认没有被别人改过。没有权限时，不泄露另一条客户记录的姓名或联系方式。

| 操作 | 身份条件 | 联系安排条件 | 谁可以做／还需什么 |
|---|---|---|---|
| 看资料、接收消息、记录真实发生的事情 | 待核实也可进行 | 各种安排均可 | 原有查看／记录权限；不自动记为成功联系 |
| 判断是否同一人 | 确有待核实关系，双方资料未被别人改动 | 可依据现有资料判断 | 配置及双方原权限符合，结论与原因必填 |
| 认领客户 | 没有任何未核实关系 | 尚未到复查日期或已停止联系，不妨碍内部认领，但之后仍不能直接联系 | 尚无负责人、原有认领资格及配置允许 |
| 分配或转交给新负责人 | 没有任何未核实关系 | 可改内部归属，不自动恢复联系 | 原有分配资格及配置允许；接收人员有效且能查看、跟进 |
| 因账号停用退回共享池 | 可以仍待核实，见第5节 | 各种安排均可 | 有分配权限的管理者，说明交接原因 |
| 普通销售联系 | 没有未核实关系 | 未停止，且不在明确约定的不主动联系期限内 | 原有权限允许即可；管理者普通协助不用先填原因，自动记录当时负责人和操作人 |
| 联系核实身份 | 确有待核实关系 | 未停止均可；停止联系时不行 | 仅有权限的管理者，指出涉及哪两条记录、核实什么、为何联系 |
| 回复客户新问题 | 没有未核实关系 | 未停止均可；已停止须先恢复 | 负责人或有权限管理者，关联真实客户消息，见第7节 |
| 恢复正常跟进 | 可仍待核实，但恢复不解除身份限制 | 取消停止限制 | 原修改安排权限、原因及后续安排齐全，资料未被别人改动 |

表中的允许均以原有权限为前提。管理者协助不是一个需要申请或批准的新流程，也不能增加资料访问范围。

## 5. 身份没核实前，怎样处理负责人和交接

1. 空电话或空邮箱造成的旧误匹配不算身份疑问，不重新加入核实名单。
2. 一条客户记录可能关联多条记录。只确认其中一对，仍有其他关系未核实的，就继续禁止认领、分给新负责人或普通销售联系。
3. 确认为同一人只保存判断，不自动合并、复制聊天、转移测评、改负责人或完成任务。
4. 已有负责人后才发现身份疑问，保留原负责人，增加联系限制，不自动清空或转交。
5. 不能先分配给销售再让销售调查。管理者从核实名单处理，不用客户负责人字段代替核实工作负责人。
6. 账号停用或收回权限需要交接时，待核实客户不能交给新负责人。有分配权限的管理者可说明原因，明确退回共享池；历史、任务和期限保留，按既有管理者提醒路线处理。
7. 客户交接不等于任意任务都自动转交。任务按现有规则明确选择，接收核实任务的人也须原本就能访问。仅交接任务不能间接改变客户负责人或扩大访问范围。
8. 停用账号本身不被核实问题卡住。没有CRM交接权限的系统管理员保留待交接事项，交给有权限管理者处理。
9. 退回共享池后仍需核实，不能借退回再认领绕过限制。

这些限制只影响新操作，不追溯改写原负责人或交接历史。

## 6. 用任务安排时间，只单独保留停止联系

不再让销售选择“等待回复”“暂缓培育”或“暂停至某日”状态。只需要安排具体任务；客户明确要求暂时别联系时，在复查任务中注明即可。

| 客户情况 | 怎样安排 | 联系限制 |
|---|---|---|
| 下周跟进，但客户没有要求别联系 | 建立下周跟进任务 | 不因未来任务限制今天的合理联系 |
| 客户明确说“11月1日前不要联系” | 建立11月1日复查任务，写明原因，勾选“此前不主动联系” | 该日期前拦截普通主动联系；日期到后限制自然结束，任务进入待处理，不自动发送消息 |
| 客户只是尚未回复 | 按原未回复规则和已有任务处理 | 不自动新增暂停或停止限制 |
| 客户明确要求不再联系 | 设置“停止主动联系”，原因必填 | 各联系入口禁止；重新联系须先明确恢复，不强制填写日期 |
| 活跃客户没有任务或其他有效安排 | 显示“未安排下一步”，提示补齐 | 这是待补齐事项，不能当成客户要求暂时不联系 |

- 到复查日期，员工决定联系、改约还是停止；不要求再点击“恢复暂停”。日期到不等于任务完成，也不会解除身份、Owner、权限或停止联系限制。
- 仅一个当前有效的“此前不主动联系”约定。改约须明确修改这项复查安排并留存旧时间、原因和操作记录，不能由另一项普通任务悄悄覆盖。
- 提前取消客户约定须明确说明原因；收到真实新咨询可按第7节回复，但不因此取消原约定。
- 原业务任务并存，截止时间及逾期保留；约定期间改为内部核查提醒，不催直接联系，不自动完成、取消或改期原任务。
- 停止联系后仍可接收消息和记录真实事实；恢复须说明原因并保留有效后续安排，不增加联系次数、不改变Owner。
- 客户分组、连续未回复计数、最后等待窗口和人工确认保护保持原规则。任务安排不代替分组，分组也不自动产生禁止联系的约定。
- 本节已实现。现有等待／培育记录保留；有明确时间的安排与已有复查任务核对，不重复创建，缺少依据时标为“安排待核对”，不猜日期、不擅自放开联系。

## 7. 联系前要说明什么用途

电话、WhatsApp、复制联系内容都按同一规则检查。本轮不新增自动发送消息。

| 联系用途 | 必须满足的条件 | 不会自动发生的事 |
|---|---|---|
| 普通销售跟进 | 身份已核实、不受停止或明确日期约定限制，符合原联系权限；管理者可直接协助，不强制填写事前原因 | 不改负责人，不把打开工具记为实际联系 |
| 联系核实身份 | 管理者、确有待核实关系，指明双方记录、要核实的问题及原因；停止联系时禁止 | 不夹带优惠推广，不自动判为同一人 |
| 回复客户新问题 | 身份已核实，关联真实客户原文；约定不主动联系期间消息须在约定生效后收到、尚无已答复记录，并说明回复范围 | 不取消原约定，不自动完成任务 |

第三项已实现为专门用途，要求关联消息、员工核对尚未答复及回复范围。员工可以回答客户的新问题，不必为了回答一次问题就取消原来的不主动联系约定。

消息必须属于当前客户且有权查看，AI或系统消息不算。管理者协助不额外要求代处理原因；约定不主动联系期间仍须关联客户原文并明确回复范围，销售仍先认领。停止联系不能使用这个例外，必须先恢复。

约定生效后收到、尚未答复等条件只用于约定不主动联系期间的例外；正常跟进中的回复沿用原权限，也可关联原文。不能把已读当已答复。无法可靠确认是否答复时，保留约定并提示核对或明确修改约定，不能无依据允许例外。

允许销售核实的配置仍不允许核实前由销售主动联系。打开工具前显示客户、号码、负责人和联系安排。普通跟进由系统记录用途，不要求员工多选一次或先填写代处理原因。仅特殊情况填写所需依据，例如联系核实身份时写明要确认的问题，不默认加入营销内容。相同联系方式不改变聊天或测评归属。

操作记录写明谁、何时、针对哪个客户、通过哪个入口操作，以及当时负责人、安排、用途、原因和关联依据。密钥或无关聊天不写入记录；研发保存字段见第14节。

**打开电话、WhatsApp或复制内容，只能说明员工使用了联系入口，不能说明已发送、已接通或已完成任务。** 员工在外部工具手输号码、改写消息、最终发送的行为，CRM无法全部控制。

## 8. 保存、多人同时操作和失败时怎么办

- 列表、详情、身份页、交接页显示同一套可操作项和限制原因；后台最终检查，不能只隐藏按钮。
- 覆盖认领、分配、交接、联系和恢复。开发前列全其他管理及导入入口；新客户仍先不分配，不批量改旧记录。
- 提交时重查权限、配置、负责人、身份和安排，不直接使用旧页面的判断。
- 身份疑问先保存，后分配就拒绝；分配先合法保存、后来才发现身份疑问，则保留负责人并立即增加核实限制，不追溯作废合法历史。
- 多人同时认领只允许一人成功。分配、恢复、联系同时发生，也按实际保存顺序重新检查；涉及多个记录时全部成功或全部不保存。
- 打开外部工具前即时检查。只能证明当时允许，不能保证工具打开后负责人永不变化；再次点击仍需检查。
- 保存失败保留输入和当前客户。没有回应先查询原来那次是否成功，或重试原操作，不因此新增两条记录。
- 查到之前已保存，不代表现在仍可联系。状态已变化时提示“之前已记录联系入口操作，当前不可继续联系”，不能自动打开工具。
- 旧页面缺少新要求的用途或依据时，说明缺少什么并提示刷新；不自行替员工选择联系用途。
- 登录失效要求重新登录；无权说明不可操作；资料不可见不泄露内容；别人已修改要求刷新。填写错误在原因或依据旁说明。
- 失败不增加联系次数、不完成任务、不产生新的外发通知。研发的保存编号、锁定顺序、错误码和结果查询细则见第14节。

## 9. 通知、历史数据和发布边界

保持先通知负责人、没有合适负责人时转给管理者的路线，原策略条件、工作时间、发送频率及任务期限不变。

发送前检查最新负责人和安排。明确约定的期限内提醒内部核查或复查，不催直接联系；身份未核实先提示核实；停止联系不催主动联系。

不启用新策略、不重新计算历史响应时限、不重建历史通知。已被外部接口接受的发送不标成已撤回，模拟发送和真实发送保持区分。不新增群、不改Webhook或密钥；使用模拟发送测试。保留失败、结果未知和已取消记录，不自动重发。接口接受不表示群内实收或员工已读，读消息不完成任务。

优先沿用现有数据结构。确需新增字段先列出增加和回退清单，不能借默认值改旧账号、配置、负责人或期限。旧记录没写用途就显示历史用途未记录，不猜测补填。

确认开发后，普通流程先在本地3000定向验证。多人同时操作、配置组合、停用交接和故障在独立MySQL模拟库中验证。推送GitHub、发布公司测试、更新禅道仍分别等待授权。

## 12. 业务决策的确认范围

用户已批准按本节及第6节收口规则实施。以下为本轮固定范围：

1. 身份未核实不认领、不分配或转交给新负责人，原负责人保留。账号停用交接时，有权限管理者可明确退回共享池。
2. 不再单设暂停状态。普通任务说明何时做什么；明确约定某日前不主动联系时，复查任务注明原因及日期。到期解除这项日期限制，不自动联系或完成任务；停止联系仍须明确恢复。没有任务表示未安排下一步。
3. 管理者可说明原因后为核实身份联系，但停止联系必须先恢复；允许销售判断身份，不代表允许销售核实前联系。
4. 约定不主动联系期间可针对真实未处理的客户新问题回复，不取消原约定；停止联系仍须先恢复。
5. 管理者普通协助直接使用联系入口，无额外审批或事前原因必填，系统自动记录且负责人不变；改变安排、判断身份和特殊联系仍需对应原因／依据。
6. 不扩大原权限，不改三个配置默认值、任务及期限、客户分类或评分，不自动合并客户。

确认本方案不等于批准状态拆分、同人历史汇总等后续项目。

以下为规则与技术实现对照；独立库及本地定向验收不等于所有并发交错或角色组合均已覆盖。

### 14.1 接口、并发、幂等及失败行为

#### 14.1.1 共同判定

新增或收敛纯动作判定器，输入当前有效员工、Lead、配置、有效身份关系、联系安排、用途及证据。输出允许动作和机器可读原因；前端用同语义展示，服务端拥有最终决定权。

覆盖现有claim、Lead PATCH Owner、CRM交接、contact-authorization及恢复流程。实现前盘点所有写Owner的管理路径和导入路径，不能只补列表入口。登记新Lead仍沿用初始未分配规则，不批量重写原数据。

#### 14.1.2 事务与并发

- 每次新动作在事务内重读有效账号权限、配置、Owner、contactArrangement版本和有效pending。配置与关系并发不能使用旧页面快照放行。
- 身份判断锁两条Lead时采用稳定ID顺序；身份发现、分配、交接使用一致的行锁顺序／配置共享锁约定。单纯重复SELECT不足以解决新候选并发插入。
- 以事务提交为边界：候选先提交，后续分配必须拒绝；分配先合法提交、随后新增候选，则保留Owner并立即追加pending限制。已有审计不追溯作废。
- 同一模拟Lead被两人认领仍只有一人成功。分配、恢复与外联授权并发时，后提交动作重新核对前置条件。
- 调用外部工具前即时请求授权。授权只能证明当时允许，不能保证工具打开后Owner永不变化。按钮每次重新执行都重新校验，不复用旧成功结果作为通行证。

#### 14.1.3 请求与结果

拟扩展contact-authorization请求：`purpose`、按用途需要的`candidateId`／`sourceMessageId`、期望Owner、联系安排版本、身份依据版本和requestId。员工身份从登录会话取得。

同一请求重试保持原requestId及内容；不同用途／客户／内容不能复用旧成功。查询返回原操作的历史结果，不再次产生业务副作用。若当前状态已经不允许，前端展示“之前已记录联系入口操作，当前不可继续联系”，不得据查询结果自动打开工具。旧客户端缺少必需用途或版本时返回可读提示，不默认为普通跟进／Manager核实。

401要求重新登录；403为当前无权；404不泄露不可见对象；409表示Owner、配置、安排或身份依据已变化；字段错误定位原因／证据。具体错误码及三语词典在实施时列明。

失败保留草稿、客户上下文和原requestId。身份pending、Owner冲突、证据不足等拒绝，不增加联系计数，不完成任务，也不产生新的外发通知。


### 14.2 任务安排与联系限制的数据实现

- 不新增暂停状态。复查动作、原因、日期与来源关联优先复用现有contact_review任务；只有明确选择“此前不主动联系”才产生日期限制，不能从任何未来任务推断限制。
- 时间限制必须有明确时区、起止依据和版本。授权与通知发送时按最新约定检查；到期自动结束时间限制，不依赖后台任务及时执行，不自动发送、完成任务或解除stopped。
- 同一客户仅一个当前有效日期约定；明确改约或提前取消保留历史，幂等及并发校验沿用现有事务。普通任务创建、完成不隐式覆盖该约定。
- 旧waiting／nurture、原因、复查时间、任务及审计不批量改写。实施前核对已有复查任务，避免重复；不完整记录保留原限制并提示核对，不猜日期。适配及迁移清单需随实施方案列出。
- stopped继续独立保存；停止原因必填，不强制日期。恢复单独记录原因及后续安排。未回复序列与Tier不因任务和限制调整而改变。

### 14.3 普通管理者协助的实现要求

- 普通联系继续由服务端校验现有权限、Owner、身份及联系安排。assisted标记可自动保留，但不能仅因assisted=true就强制reason。
- 普通跟进用途由入口自动传入，不增加一个管理者审批或手动用途选择步骤。记录actor、leadId、当前Owner、时间和action。
- identity_verification仍需候选依据及待核实问题；customer_reply在明确约定期间仍须关联客户原文与回复范围。恢复安排、行政退回共享池及身份结论仍保留各自原因／依据。
- 前后端已同步移除普通协助原因必填；核实文案独立于营销模板。约定期回复由员工明确核对尚未答复，打开工具不标记已答复；保存关联有效联系结果时可明确确认实际已答复。

### 14.4 本轮接口与存储字段

- 跟进保存新增可选`reviewPlan`：创建／改约使用`{reason, blockBefore, version}`并复用`nextAction`、`nextPurpose`、`nextFollowUpAt`；提前结束使用`{cancel:true, reason, version}`。`contactArrangement`新写只接受`active`／`stopped`。旧等待／培育数据只读保护，不批量回填。
- 当前约定保存在`profile.contactReview`：`taskId`、`reviewAt`、`reason`、`blockBefore`、`at`、`actor`，关联现有`contact_review`任务。所有安排修改复用`contactArrangement.version`，保存时核对`expectedArrangementVersion`，无新增DDL。
- 联系授权须提供`purpose`、`expectedOwner`、`expectedArrangementVersion`及幂等`requestId`。身份核实需`candidateId`、`reason`；约定期回复需`sourceMessageId`、`replyConfirmedUnanswered:true`及`reason`，消息必须为本客户真实用户消息且在约定后收到。
- `sourceMessageAnswered:true`仅在关联用户消息的实际接通／回复记录中允许；不从已读、打开工具或普通关联推断已答复。员工明确核对是业务声明，不宣称CRM已监测到外部工具真实发送。
- 保存结果新增`contactPlanChange`，区分安排复查、结束约定、停止、恢复；保留实际完成任务和新增任务编号。
- 停用交接沿用现有管理操作编号／结果查询；授权Manager用`targetId=__shared_pool`退回所选客户，不支持借此单独转交任务或扩大访问范围。
