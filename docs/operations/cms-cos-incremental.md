# 既有数据库的对象存储（COS）增量升级

本项目的对象存储使用腾讯云 COS，数据库字段为 `cos_url`。本文件说明的是 **已有应用数据库的增量升级**，不是全库初始化、开发库整库导出或业务数据覆盖。

## 使用哪个文件

- 执行文件：[`v20261105220918_cms_cos_incremental.sql`](../../sql/v20261105220918_cms_cos_incremental.sql)（位于统一的 `sql/` 增量目录，命名规则见 [`sql/README.md`](../../sql/README.md)）。包含208个已提交正式媒体的真实COS URL、对象键和字节数。
- 生成器：`scripts/generate-cms-cos-incremental.mjs`。维护者使用Node 24或以上从仓库正式种子生成SQL；数据库使用者执行已生成SQL不需要Node，也不需要任何人的私有备份或验收脚本。
- 数据来源：`cloud/mysql/seeds/cms/v2`，由 `loadCmsSeed()` 校验媒体文件摘要。不能用本地验收数据、账号备份或客户记录生成此公开于项目的增量文件。
- 空库初始化是另一项操作，见[CMS COS存储与生产初始化](cms-cos-bootstrap.md)。**不要向已有业务库导入完整初始化包。**

## 变更范围

1. 核对并补齐COS v16媒体结构：`storage_type`、`cos_url`、`object_key`、`byte_size`、存储索引，以及 `content` 可空约束。已存在正确结构不重复添加；不修改其他迁移版本、排序规则或已有外键。
2. 将208个正式映射中目标库实际存在的媒体补齐为COS元数据。已有BLOB验证摘要和长度，已存在不同COS元数据时停止，不覆盖冲突对象。
3. 以目标库自己的当前CMS内容为准，仅替换已知图片字段中的匹配旧图片地址。保留文案、发布状态、排序、slug、自有新增记录、多图顺序和裁剪参数。
4. 只有内容中的图片引用实际变化，才递增该条内容版本和所属集合revision；重复执行已完成的数据不应继续递增。
5. **保留旧BLOB**、上传人、时间及legacy别名，作为旧地址兼容与恢复依据。本SQL不是旧BLOB清理脚本，也不会上传或删除COS对象。

不覆盖账号、密码、权限、CRM推广活动、客户、财务、消息、通知任务或审计历史。不导入dev额外的验收媒体。

### 自有内容与图片

同事在本地对文案、状态或排序作出的修改不会被仓库种子内容替换。SQL中的208个媒体映射并不代表每个目标库都必须恰有208条媒体或106条CMS内容。

不在正式映射中的自有图片保持原样，并列入未覆盖统计；SQL不能为未知图片凭空生成已上传的COS对象。正式图片引用缺少必要媒体记录、摘要不一致或结构异常时，应停止处理，先调查原因，不以重新导入整套种子解决。

## 执行前

1. 拉取包含此次SQL和COS运行代码的main版本。代码应先在功能分支开发和验证，再合入main；不得为了升级直接覆盖其他开发者在main上的改动。
2. 使用支持此脚本的 **MySQL 8**，在全新的严格模式、autocommit连接中执行，不夹在已有业务事务中。MariaDB和其他兼容实现未按同等语义验收。
3. 核实当前连接的主机及选中的数据库，至少执行 `SELECT DATABASE(), VERSION();`。SQL不包含连接凭据、不硬编码库名，也不替用户决定生产目标。
4. 使用现有备份方案备份目标原结构、媒体BLOB和CMS内容及版本，检查备份可读取。保留原账号与业务数据；不要把开发库的运行记录作为生产备份。
5. 安排CMS维护窗口，停止人工编辑和图片上传。脚本的锁不能替代整个应用的维护协调，不停止通知服务、不改变发送模式。
6. 检查执行账号具有所需读取、更新、迁移状态写入、ALTER、索引、临时表以及存储过程创建/执行/清理权限。不要为方便向应用日常账号永久授予DDL权限。
7. 确认COS公开图片可访问。SQL内的摘要检查只核对数据库中的BLOB/映射，**MySQL SQL本身不能代替对COS远端字节的HTTPS核验**。

## 执行方式

推荐使用**新的 mysql 命令行批处理进程**，通过标准输入重定向完整文件。先配置自己的安全登录配置和可信TLS设置，明确指定目标数据库。例如在Bash或Windows CMD中执行（替换示例登录配置名和库名）：

```sh
mysql --login-path=portal --database=YOUR_DATABASE < sql/v20261105220918_cms_cos_incremental.sql
```

此示例的 `<` 是Shell重定向语法，不是SQL，也不能原样当作PowerShell命令使用。登录配置由执行者管理，文件不包含密码。**禁止 `--force`；任何错误必须使整个批处理立即终止。普通交互式 `SOURCE` 默认可能遇错继续，不作为安全等价执行方式。**

也可使用支持 `DELIMITER`、且已明确配置为**第一条错误立即终止整个脚本**的数据库GUI执行完整文件；无法确认此行为时使用上述批处理方式。不要逐段选中执行或移除异常处理。普通驱动的单次 `query()` 不会自动解释客户端 `DELIMITER` 指令。

脚本会使用专有过程 `uper_cms_cos_20261105_apply`、`uper_cms_cos_20261105_transform`、`uper_cms_cos_20261105_ref` 及临时映射。成功后清理这三个过程；出现同名过程残留时，先检查此前运行状态和对象来源，不要盲目删除或覆盖同名对象。过程清理需要 ALTER ROUTINE 权限。以脚本实际错误与结果集判断成功，不以客户端“已发送”判断事务已提交。

## 执行后检查

- COS列和索引的实际定义正确，v16状态与实际结构一致；不能仅看最大迁移版本。
- 结果字段：`schema_ddl_changed`、`schema_version_changed`、`media_changed`、`media_skipped_unknown`、`manifest_media_absent`、`collections_changed`、`items_changed`、`refs_changed`、`refs_uncovered`、`blobs_cleared`。其中 `manifest_media_absent` 表示清单中目标库不存在的媒体数量，不等同于已存在CMS内容有断链；已知引用缺失媒体会报错。`blobs_cleared` 应始终为0。
- 相同数据库再次执行时，已迁移的媒体和CMS引用应无新增变更，版本不重复递增。
- 原有账号、文案、状态、排序、多图/裁剪参数及业务数据保持；旧BLOB仍在。
- 部署支持COS的应用，并按现有部署方式设置服务端COS凭据后，另外验收后续上传、保存和旧图片地址读取。**执行本SQL并不自动部署应用，也不配置COS上传密钥。**

存量旧应用即使能继续读取保留的BLOB，仍可能继续创建本地图片地址；不能因此宣称后续上传链路已经完成COS改造。

## 失败、中断与恢复

- MySQL DDL会隐式提交。结构升级与内容事务不是一个可整体回滚的事务；DML失败不意味着先前成功的ALTER自动撤销。
- 结构/迁移状态异常或部分完成时先核对实际列、索引及版本记录，不能只改ready标记，也不能反复执行ADD COLUMN碰运气。
- 内容事务内出错应回滚媒体和CMS数据修改；连接中断导致结果未知时，先只读检查实际数据和版本，不直接恢复旧备份覆盖后续编辑。
- 从备份恢复时只恢复确认属于本次的目标数据，检查是否已有后续修改；通常保留正确完成的v16兼容结构，不删除整表或重建数据库。
- 未经独立确认不清空BLOB、不删除COS对象、不重放通知。
