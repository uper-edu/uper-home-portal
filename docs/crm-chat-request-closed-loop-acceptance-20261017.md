# Chat 请求、系统确认与跟进任务闭环验收

日期：2026-10-17。范围：独立本地 4426、独立 MySQL、模拟客户。未切换 3000、未推送 GitHub、未部署服务器。

## 结论与证据边界

原 Conversations 混合样本是直接写入数据库的界面压力测试数据，其中普通课程咨询后排列了多个无对应客户表达的系统事件。它能检验显示效果，**不能证明 Chat 自动识别请求或创建任务**。本轮保留其历史原文，停止将它作为触发逻辑验收依据，改用下列真实浏览器入口产生的样本。

此前独立 `/chat` 未与主页助手统一请求路由，预约、报名文字会进入普通 AI 咨询。本轮补齐共享客户端的明确请求路由，并修复同类请求重复建任务的风险。未扩展 Tier、评分或 AI 自主销售决策。

## 系统确认的含义

客户明确表达请求后：

1. 保存客户原话。
2. 新建或复用同类未完成跟进任务，保存请求与任务的关联。
3. 返回“请求已记录”的系统确认消息。
4. 销售在 Follow-up 中记录结果、明确选择完成任务。查看消息不会完成任务。

确认消息是历史收件凭据，不是预约确认、报名成交、已付款或顾问已联系。当前进度由任务状态和截止时间决定，不能从旧确认文字推断。

- `messages`：客户原话、原始确认消息；`metadata.followupAction` 和 `metadata.taskId` 区分事件并关联任务。
- `followup_tasks`：当前任务、负责人、状态、原截止时间及来源。
- `crm_facts`：每次请求补充的 `task.request_evidence`，以及销售跟进事实。
- `outbox`：新建请求任务的业务事件，交由现有通知策略决定发送；重复表达不会重复生成同一任务的请求创建事件。

三语系统说明和操作指南已同步说明以上区别。

## 实现边界

主页助手和独立 `/chat` 共用有限、保守的三语明确表达识别。典型明确请求可进入顾问联系、预约或报名接口；普通问题、否定、条件、引用示例和冲突意向继续进入 AI 咨询。该机制不是任意语言理解，不保证覆盖所有自然表达。

同类未完成任务即使来自另一会话也复用原任务，追加来源事实，保留截止时间；不同类型的请求可并存。相同请求 ID 的重试复用结果，不重复写消息。已经完成的任务不阻止后续新请求创建新任务。

## 剩余问题

1. 请求识别是受限表达匹配，不覆盖任意改写或多意图；未识别内容仍保存为对话及待核实信息。未接入 WhatsApp 消息同步，也没有在线人工坐席。
2. 同类任务复用时新请求依据已保存，但任务的主要来源仍保留首次请求。界面可进一步显示“已补充现有任务”、任务动作、当前截止时间和状态，避免销售只看到技术性的“回执”。这一展示建议需与历史事件和当前状态明确区分，不能把所有重复表达写成“任务已创建”。
3. 客户明确否定先前意向不会自动取消原任务；销售须结合最新原话处理，避免系统凭单句覆盖既有业务安排。
4. 真实 AI 通路通过不代表回答中的排课、课程来源或讲师事实已核实。该样本包含课程和讲师相关断言，仍需按实际知识来源另行审查；本轮不据此确认产品事实或修改客户评分。
5. 本轮没有真实销售参与，也不证明转化率或销售效率提升。
