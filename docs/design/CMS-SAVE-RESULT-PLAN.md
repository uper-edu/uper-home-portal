## 问题与最小方案

正常保存和上传闭环本次通过，但响应丢失不等于保存失败。当前内容保存已有requestId、输入指纹及事务内cms.mutation审计，可优先复用，不另造一套业务审批。

1. 内容保存／删除：新增只读GET /api/cms/operations/:requestId，沿用CMS身份认证，按当前操作人、requestId及集合授权查询。返回committed（原响应、条目ID、版本）、not_found（截至查询时无提交证据）或unavailable（不能查询）。无权限拒绝，不泄露他人内容。不把not_found说成最终失败或安全重提许可，因为原请求可能仍在进行。
2. 页面收到正常成功响应才显示已保存。网络断开、超时、无法解析及不明确的5xx归为“结果尚未确认”，保留原请求和冻结提交内容，显示“查询保存结果”。不得自动换ID再次提交；未找到时允许继续查询，或用完全相同的请求ID和内容进行幂等重试。明确校验失败／权限拒绝／版本冲突分别解释并保留草稿。
3. 查询确认成功后回读当前条目，区分“本次已提交的版本”和随后他人更新的版本；不把历史响应当成当前最新版。刷新后仍能找回待确认操作。仅保存必要请求上下文，不能在浏览器长期保存图片base64或秘密。
4. 图片上传与内容保存仍分开。现接口按转换后的WebP摘要去重，但没有客户端可查询的上传请求ID。建议为上传加入requestId及同事务结果记录，返回资源摘要、URL、MIME和大小；查询只返回资源元信息，不回传图片二进制。上传未确认前禁止重复上传和内容保存；确认后把URL写回草稿。不能将取消内容编辑描述为撤销上传。
5. 删除不在本轮实现范围：先复用同一查询模型设计，实际永久删除验收需另确认；不通过恢复或重复删除猜测结果。

## 验收标准

- 正常保存、再次编辑、上传→内容保存→刷新图片仍可读。
- 响应丢失后查询可确认已提交；原请求重试不重复新增内容／审计；修改请求内容却复用ID须拒绝。
- 原请求仍进行、查询未找到时不误报未保存；查询服务失败保留草稿。
- 他人请求、无CMS权限、版本冲突拒绝；不覆盖其他内容。
- 上传结果可查询、相同请求不重复写资源；不混淆上传和内容保存。

故障注入不在3000直接进行。实施前另确认安全验证范围；本方案不授权独立环境、通知实发、删除、推送或部署。
