## 1. 发布前准备

1. 锁定获批提交和范围。审查启动迁移、初始化和历史数据影响。涉及 Enrollment 时，销售与财务核对新报名、凭证、核款、退款和商机的验收证据。已上线的旧款项按原记录核对。
2. 对最终待同步版本完成 `npm test`、`npm run lint`、`npm run build` 和 `git diff --check`。另执行 `npm run build:prod` 生成正式制品，记录提交、构建编号和校验值。保留上一版制品。
3. 按正式环境部署方式核对域名、代理、TLS、数据库和运行配置。已有私有配置只补缺项，保留现有值及有意留空项。凭证和解密密钥保存在正式私有配置及受控备份中。
4. 备份数据库、运行配置和凭证解密所需密钥，记录恢复证据。对照允许变更范围记录账号权限、客户归属、报名、实收和退款余额及队列基线。涉及结构和数据变更时，先在获准的隔离环境验证升级及回退。
5. 按批准的窗口暂停受影响写入和队列消费。记录在途发送及恢复条件，完成下表中适用的配置核对。

### 1.1 存量数据与升级演练

放行标准是每一项存量数据变化都能由已批准的迁移规则或正常业务操作解释。只升级应用时，验收应确认升级本身未改写存量业务数据。涉及数据迁移时，先列明允许变更的表、字段、记录范围和预期结果，再逐项核对。

- [ ] **发布负责人** 审查启动时自动执行的迁移和初始化，明确哪些操作会新增或更新记录。测试站的清库、账号重建和统一初始密码步骤不得用于生产。
- [ ] **运维** 发布前完成可恢复备份并记录恢复点。在隔离库验证恢复；按发布方案记录生产基线，包括客户及归属、账号角色、历史报价、报名、款项、任务和通知队列。使用汇总及校验值留证，避免在验收记录中保存密码、凭证和客户原文。
- [ ] **财务** 按报名项目对照历史标准价、优惠、最终应收、逐笔到账及退款、作废状态和余额。总笔数和总金额一致后，继续核对逐笔差异，防止相互抵消掩盖错误。
- [ ] **运维与业务验收人** 用一致的业务时间点比较前后结果。发布窗口内允许正常写入时，结合审计和流水区分正常业务变化与升级写入。无法区分时，暂停受影响的写入后再核对。上线后的只读验收也按同一标准复查。
- [ ] **放行人** 确认未发现未经批准的删除、覆盖、重复记录或权限变化。有无法解释的差异时，暂停放行和受影响的写入，保存差异证据，按第 6 节决定修复或回退。备份仅作为恢复手段，不能替代前后核对。

数据库结构、初始化规则、历史数据读写或通知队列有变化时执行。纯文案或样式发布可注明不适用。

1. **建立隔离环境。** 从当前生产版本开始，使用经授权的脱敏快照或具有同等结构的样本。覆盖旧报名缺课程明细、旧报价、部分付款、退款、作废、待核验、旧员工角色及未完成任务。使用隔离数据库和模拟通知端，启动前核对连接目标及外发隔离。
2. **记录升级前基线。** 保存客户、报名、款项、课程、账号角色和队列计数。逐笔记录样本的应收、到账、退款和余额，并备份数据库及旧版本运行配置。
3. **执行拟上线步骤。** 使用同一目标制品和迁移顺序，记录耗时、锁等待、失败点及允许的写入窗口。再执行一次启动或初始化，确认不会重复创建课程、Campaign、角色或通知。
4. **核对升级结果。** 对比基线及事先列出的预期差异。旧报价、历史款项、权限与客户归属应符合原记录。测试新增报名和收款核验。检查旧待发任务的处置及是否有历史通知重放。
5. **演练回退。** 先验证旧应用能否读取升级后的数据。若不能，在隔离库实测备份恢复，并用一条模拟升级后新业务演练增量导出、补录和对账。记录实测恢复时长、可恢复时间点和负责签核的人。

- [ ] 演练记录、差异和恢复证据齐全，发布负责人确认可在窗口内执行。

### 1.2 正式招生签核

每项记录负责人、状态、证据及时间。关键项失败或证据不足时暂缓放行。不适用项注明原因。全量测试的跳过数照实保留，影响本批的跳过项单列补验结果。

| 负责人 | 通过标准 | 证据、状态及时间 |
| --- | --- | --- |
| 运营、教务 | 确认首批班次的首课、每周课表、停课日、教师、课时、实付价格、优惠及招生上限。只签核本次开放班次。 | |
| 财务、客服 | 核对人工转账的银行、户名和账号、退款公示和客服入口。以模拟订单确认应收、到账、退款及余额逐笔一致，重复提交只记一次。 | |
| 销售运营、财务 | 公司 test 用模拟数据复验英文和印尼文手机端。由具体推广短链进入报名，完成收码、获席、付款说明、传凭证和 CRM 核款。核对推广归因，覆盖满班、断网恢复和重复提交。 | |
| 系统管理员 | 按发布影响验证销售、财务、经理和无权限账号的客户范围、直接访问及接口拒绝。涉及账号变更时复验改密和重置后的首次改密。 | |
| 运维、系统管理员 | 核对正式域名、密钥环、发信池、SMTP 凭证与额度、旧队列和在途回执。经单独授权用指定邮箱验证真实收码、邮件链接及原订单回跳。 | |
| 放行人 | 确认正式制品、备份、回退方案和上述签核齐全，记录新报名开放时点及首批订单观察负责人。 | |

本批验证以 [Enrollment 验收记录](requirements/enrollment-v1-release.md) 为证据。区分公司 test 冒烟、独立 MySQL 模拟和真实投递。手机性能记录目录可操作、验证码到达、获席结果与凭证回读耗时，注明网络、样本量和失败率。

## 3. 生产环境变量

与 `.env.prod.example` 对照填写。私有值由运维通过正式应用的运行配置提供。模板使用 `UPER_PORTAL_` 命名，运行入口仍可读取已有的 `PORTAL_` 变量。切换时同一项只配置一次，新旧值冲突会中止启动。旧版回退使用该版本对应的私有配置。

### 运行与站点

生产启动必须满足环境与部署门禁。端口与前端目录按实际部署方式配置。

| 变量 | 用途与配置时机 |
| --- | --- |
| `UPER_PORTAL_ENV` | 生产环境标识，须与构建包目标一致。 模板值为 `prod`。 |
| `UPER_PORTAL_ENV_SOURCE` | 容器注入完整配置时用 `injected`。由启动器读取私有环境文件时可省略。 模板值为 `injected`。 |
| `UPER_PORTAL_DEPLOYMENT` | 启用正式站部署校验。 模板值为 `production`。 |
| `UPER_PORTAL_PRODUCTION_READY` | 启动门禁。生产部署前确认配置及前置签核后设为 `true`。模板值为 `false`。 |
| `NODE_ENV` | Node.js 正式运行模式。 模板值为 `production`。 |
| `APP_ENV` | 启用正式环境访问保护。 模板值为 `production`。 |
| `PLATFORM_MODE` | 使用本站员工账号和本地身份模块。 模板值为 `local`。 |
| `PORT` | 容器监听端口，缺省 `8080`，须与反向代理一致。 |
| `APP_URL` | 正式站规范 HTTPS 地址。 模板值为 `https://uperedu.com`。 |
| `UPER_PORTAL_PUBLIC_ORIGIN` | 用于登录和写入的来源校验、生成招生邮件链接及校验 Lark 回调。 模板值为 `https://uperedu.com`。 |
| `TRIAL_FRONTEND_DIRECTORY` | 由应用提供静态站点时，填实际前端构建目录。 |

### MySQL

应用默认使用 MySQL。显式设置其他数据库类型会中止启动。

| 变量 | 用途与配置时机 |
| --- | --- |
| `TRIAL_DATASET` | 正式连接的校验标识，设置此值不会初始化或清除数据。 模板值为 `synthetic`。 |
| `MYSQL_TRIAL_URL` | 正式数据库私有连接地址，使用经批准的生产库和内网端点。 |
| `MYSQL_TLS_MODE` | 正式站启动校验要求经批准的内网 MySQL 直连模式 `disabled`。 模板值为 `disabled`。 |

### 访问保护与后台任务

| 变量 | 用途与配置时机 |
| --- | --- |
| `ACCESS_ALLOWED_ORIGINS` | 正式站获准的 HTTPS 来源清单，须包含主站。多个来源以逗号分隔。 模板值为 `https://uperedu.com,https://www.uperedu.com,https://home.uperedu.com`。 |
| `ACCESS_TRUSTED_PROXIES` | 可信反向代理的具体私网 IP，多个地址以逗号分隔。 |
| `UPER_PORTAL_WORKER_ENABLED` | 后台 worker 开关。省略时正式站默认开启。首次部署核验或维护时显式设为 `false`。 模板值为 `true`。 |

### 集成凭证与浏览器统计

| 变量 | 用途与配置时机 |
| --- | --- |
| `UPER_PORTAL_CREDENTIAL_KEYRING_FILE` | 后台集成凭证使用的生产专用密钥环。使用托管凭证时提供容器内可读的绝对路径，文件权限为 `0600`，与数据库独立备份。 |
| 浏览器 GA4 数据流 | 前端按构建目标读取 `src/data/analyticsEnvironments.json`，更改映射后重新构建。 |

### 报名与招生邮件

| 变量 | 用途与配置时机 |
| --- | --- |
| `UPER_PORTAL_ENROLLMENT_SERVICE_ENABLED` | 默认关闭。权限和存量订单服务联调通过后启用，包括查单、补交凭证、核款和退款。 模板值为 `false`。 |

### 按需配置

| 变量 | 用途与配置时机 |
| --- | --- |
| `UPER_PORTAL_LOG_LEVEL` | 调整日志级别时填写。 模板值为 `info`。 |
| `MYSQL_BIN_DIRECTORY` | 备份或恢复工具找不到 MySQL 客户端时填写。 |
| `ACCESS_INITIAL_PASSWORD` | 全新生产库首次启动前，由部署层从私有配置注入。若启动器读取环境文件，在私有 `.env.prod`（权限 `0600`）中填写。预置账号首次登录必须改密。确认账号初始化成功后，可从私有配置移除此项。 |
| `UPER_PORTAL_BOOTSTRAP_SECRET_FILE` | 部署层按需指定启动凭证私有文件的绝对路径，可提供数据库连接和首次初始化所需的临时密码。初始化成功后只移除临时密码条目，保留仍在使用的连接配置。 |
| `UPER_PORTAL_CREDENTIAL_PROVIDER_CHECKS` | 仅获准调用真实供应商核验时启用。 模板值为 `false`。 |
| `OPENAI_MODEL` | 可选的初始模型覆盖。已有后台配置时以后台为准。模板示例已注释。 |
| `UPER_PORTAL_COS_BUCKET`、`UPER_PORTAL_COS_REGION`、`UPER_PORTAL_COS_PREFIX` | 省略时使用代码内置目标。若存量部署显式提供这些值，必须与已批准的桶、区域及 `cms/` 前缀一致。 |

### 存量升级与回退

新部署按当前模板和后台配置准备。仅当目标生产库还在读取旧环境来源、解密旧密文，或尚未迁移投递模式时，才核对并沿用对应旧值。按[集成凭证切换与恢复](integration-credentials-runbook.md)逐项确认当前生效来源、重启回读及回退材料，再清理旧配置。旧版本所需配置随该版本的回退备份保管。

若首次跨过招生邮件投递方式迁移，先核对原投递模式和旧队列。运行时只在首次迁移读取旧传输变量，日常切换在后台保存。若首次跨过账号操作密钥下线，按[启动文件清理步骤](integration-credentials-runbook.md#部署文件和系统设置)检查旧私有文件。旧操作密钥已不在启动密钥文件的允许清单内。

## 5. 切换与放行

1. 使用已登记的正式站部署操作切换到目标制品。按演练顺序执行迁移和初始化，记录完成时间及影响。核对 `/api/health` 和 `/api/version`，确认前后端版本一致、数据库正确、日志无启动异常。
2. 恢复邮件消费前，按 [旧队列操作清单](requirements/enrollment-mail.md#发布前旧队列操作清单)备份并审核事件键。命令先预览，确认后以同一组键加 `--apply`。核对未发旧件、有效报名成功邮件、模拟回执及保留项，再预览确认新增为零。正式运行前验证清理脚本可从目标源码和运行配置执行。
3. 销售、财务和管理员分别只读抽查入口、权限和存量记录。经另行授权的测试写入或真实发信按批准场景、账号及收件地址验收。发信获准后核对发件人、实际收件和邮箱验证回跳。
4. 由放行人签核差异、队列处置和观察安排。按批准顺序恢复写入、后台及各渠道消费，观察错误、重复投递、账务和积压，记录结果。

<a id="production-lark-release"></a>

### 5.1 Lark 通知切换

涉及 Lark 时，发布前备份运行配置并记录群与个人渠道模式、签名、目标、收件策略和排队状态。核对正式租户、应用、员工绑定与固定回调 `https://uperedu.com/api/crm/lark/callback`。凭证来源和旧值退役按第 3 节执行。

首次升级涉及旧渠道模式迁移时，保持 worker 暂停，沿用原生效的兼容配置。仅当旧 `PORTAL_NOTIFICATION_MODE=configured` 且群渠道原为真实发送时保留群真实投递。个人渠道还要求旧 `LARK_PERSONAL_DELIVERY_ENABLED=true`。其余按模拟模式核对。确认保存结果后再按旧版升级兼容流程清理相应变量。

复核待发任务、目标群和员工绑定。若获准演练新绑定或换绑，先确认个人渠道处于模拟模式。待渠道和队列处理方案获批后恢复 worker，观察积压和重复外发。

### 5.2 生产测试记录

**生产默认只读验收。** 当前生产写入隔离能力应在每次发布前实际确认。仅添加测试名称无法隔离报表、通知或自动任务。

- [ ] 写入前记录批准人、范围、期限、负责人及预期副作用。验证测试记录能与真实客户、统计、自动分配、提醒、外部通知和分析事件隔离。任一隔离项无法验证时，把该写入场景移到测试环境。
- [ ] 统一使用 `TEST-发布编号-场景`，登记客户、报名、草稿等记录的编号与关联。只使用专用测试身份和接收端。
- [ ] 验收结束按登记编号逐项处理。草稿和专用测试客户在确认关联后走受支持的归档或清理流程。已形成业务历史的误记由有权限人员按业务流程作废并注明原因，保留核验及审计记录。
- [ ] 清理后核对余额、报表、任务和待发队列。另行核查已外发消息或已上报事件，因为清理 CRM 记录无法撤回这些结果。记录遗留项、负责人和处理期限。

## 6. 停止与回退

健康或版本不一致、关键权限异常、金额差异、迁移失败或误发时，停止放行并隔离受影响的写入或外发，保留日志、记录编号和发送回执。确认旧应用兼容当前数据库后方可回切旧制品。需要恢复数据库时，由回退决策人批准恢复点，先登记切换后的新增业务及对账安排，防止恢复覆盖已发生的收付款。回退后复核健康、版本、账务和队列状态。

招生放行前，在「报名管理 → 课程与班次设置 → 报名规则」核对正式收款账户，在「招生邮件」核对发信池和招生就绪提示。先验证存量订单链路，再按签核顺序启用正式投递。报名服务与收款账户、验证码投递就绪后，新报名自动开放。收款配置缺失时，已验证学员仍可查单及补交凭证。就绪提示核对保存的配置，正式 SMTP 的实际投递另行联调。
