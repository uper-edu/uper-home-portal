# 集成凭证配置、切换与恢复

适用于本地、公司测试和生产。每个环境独立准备私有文件、供应商凭证及数据库备份。现有环境按单项凭证切换。

## 单个集成如何切换

「集成配置」默认打开「AI 模型服务」。用左侧目录切换集成。「Lark → 应用与员工绑定」可直接编辑并使用标题右侧的「保存」。密钥、Webhook 和 Secret 通过对应行的「管理凭证」维护。Google Analytics 的 CRM 事件外发有独立的启停操作。

| 集成 | 管理入口 | 核验的范围 |
| --- | --- | --- |
| OpenAI／DeepSeek／Anthropic (Claude)／MiniMax | **系统管理 → 集成配置 → AI 模型服务 → 供应商凭证** | 用该供应商当前配置的模型核验流式、结构化回复和提取。更换凭证后，使用同页的 **测试当前配置** 核对生效的主备模型。修改模型时使用 **测试并保存**。 |
| 招生 SMTP | **系统管理 → 邮件配置 → 发件账号 → 管理凭证**（账号行或邮箱详情） | 核对账号、主机及端口。密码核验检查连接、TLS 和身份验证。随后按招生邮件验收流程检查发信池、额度、投递开关和报名状态。 |
| Lark 群 | **系统管理 → 集成配置 → Lark → 群通知** | Webhook 和启用签名时的签名密钥成组保存。CRM 通知渠道可打开同一份凭证。实际投递测试沿用独立授权。 |
| Lark 应用 | **系统管理 → 集成配置 → Lark → 应用与员工绑定** | App ID、租户标识和 OAuth 回调地址原样迁入后台后，确认密钥与现有绑定回读，再移除对应的三个环境变量。已有员工绑定时锁定 App ID 和租户。回调地址仅接受本环境站点的 `/api/crm/lark/callback`。 |
| GA | **系统管理 → 集成配置 → Google Analytics** | 人工核对环境、衡量 ID 和对应数据流的 Secret。此核验阶段不会发送事件。实际出站仍须配置并授权独立的 GA 外发开关。 |
| COS | **系统管理 → 集成配置 → 对象存储** | 成组提供 Secret ID、Secret Key 及临时 Token（按需），核对桶、区域、前缀和只读连接。在获准的目标环境另验证 CMS 新图片上传权限。 |

1. 起始先在 **系统管理 → 集成配置 → 环境就绪状态** 核对本环境数据库、凭证主密钥和恢复签名。运维记录备份以及上版制品。应用启动迁移只建表，已有配置和旧密文继续可用。
2. SMTP、OpenAI、DeepSeek、Anthropic、MiniMax 和 Lark 应用使用 **核验并保存**。系统管理员可在各环境主动发起供应商核验，成功后才保存凭证。Lark 应用可直接 **更换密钥**，新密钥取令牌成功后生效，核验失败继续使用当前密钥。
3. Lark 群和 GA 使用 **核对并保存**。已有凭证先撤销再设置。群渠道需核对 Webhook 目标，开启签名时同时填写签名密钥。GA 需核对当前环境、衡量 ID 和同一数据流的 API Secret。保存不触发投递。对象存储继续用候选、核验和启用流程，候选核验回执有效期为十五分钟。
4. 核验失败时检查凭证、目标和权限。若页面显示结果待确认，按操作 ID 查询后再继续。真实投递或写入使用相应的独立验收流程。
5. 重新启动同环境版本，确认凭证状态为「已配置」，并在变更审计核对启用记录。检查该集成自己的重点业务路径及其发送门禁。逐项移除已完成切换的旧环境值，其他账号和集成可继续沿用旧来源。归档对应旧解密密钥至旧备份过渡期结束。撤销后的账号、目标变化或缺少密钥会在状态中显示，运行时停用该凭证。若凭证疑似泄露，及时在供应商处撤销对应凭证，已经开始的请求由供应商和现有回执规则处理。
6. 第三方凭证由系统管理员管理。SMTP 及 AI 供应商更换凭证时先撤销当前凭证。撤销 AI 凭证前核对主备供应商可用性，凭证撤销或保存成功后，先前的模型测试回执失效。邮件配置、通知渠道的其他业务操作沿用原有权限。变更可在 **系统管理 → 用户与权限 → 变更审计** 核对。

Claude Haiku 5.5 和 Claude Sonnet 5.5 共用同一环境的 Anthropic 凭证，可分别配置为主模型或备用模型。主备选择同时适用于 Chat、CRM 结构化提取和学习目标比对。保存凭证后，再用「测试并保存」启用选中的主备配置。两款 Claude 共用同一家供应商，Anthropic 整体故障或凭证失效时，跨供应商主备才能提供额外的故障隔离。

### 配置 AI 供应商

1. 在「AI 模型服务 → 供应商凭证」，OpenAI、DeepSeek、Anthropic（Claude）和 MiniMax 均为预置项，直接打开「管理凭证 → 设置 API 密钥」。MiniMax 使用中国站 `https://api.minimax.cn/v1/chat/completions`，原国际站凭证须更换为中国站密钥。
2. 「核验并保存」检查 JSON 回复、流式回复和 CRM 结构化提取。Claude 密钥同时核验 Haiku 5.5 和 Sonnet 5.5。已验证且与当前地址相符的凭证可直接使用，历史上只核验过一款 Claude 型号的凭证须重新核验后才能使用另一款。
3. 两个主备下拉始终列出完整型号，可用性随凭证核验结果更新。选好模型后用「测试并保存」切换运行配置。供应商凭证的保存与撤销不会改动当前主备型号。
4. 需停用某供应商时，先切走正在使用的主模型或备用模型，再撤销该供应商凭证。

已通过旧网关使用 MiniMax 的环境继续按原配置运行。配置同一模型的官方直连密钥前，先切换到其他已核验模型。MiniMax 直连使用该供应商独立核验的密钥。

## 部署文件和系统设置

| 设置 | 放置位置与默认值 |
| --- | --- |
| `PORTAL_BOOTSTRAP_SECRET_FILE` | 私有运行配置里填绝对路径。文件为 dotenv 格式，接受 `MYSQL_TRIAL_URL`、`ACCESS_INITIAL_PASSWORD` 和旧版按需使用的 `ACCESS_INITIAL_PASSWORDS_FILE`。所列变量以私有文件值为准。首次初始化员工后可移除初始密码。 |
| `PORTAL_CREDENTIAL_KEYRING_FILE` | 私有运行配置里填绝对路径。配置文件权限为 `0600` 或只读 `0400`。以运行账号直接读取文件，容器以只读方式挂载到容器内路径。文件需独立于数据库快照。 |
| `ANTHROPIC_API_KEY` | 可选的私有环境凭证。优先在「供应商凭证」管理 Anthropic，托管凭证撤销后沿用现有规则停用环境来源。 |
| `PORTAL_GA_DISPATCH_ENABLED` | 默认 `false`。授权外发前保留关闭。升级原本已开展 GA 外发的站点时，单独确认连续发送或暂停及队列范围。 |

密钥文件是 JSON 对象，字段为 `environment`、`active` 和 `keys`。`environment` 为 `dev`、`test` 或 `prod`，`active` 为当前写入的密钥 ID。`keys` 按 ID 保存各版本密钥，每个值为 32 个随机字节的 64 字符十六进制编码。目录应只允许运维和运行账号按需访问，文件放在仓库及发布包之外。密钥版本可按受控备份策略保留和归档。

迁移期间，仍在使用旧 SMTP 密文的环境须保留对应的 `PORTAL_ENROLLMENT_MAIL_CREDENTIAL_KEY`。旧生产 Lark 加密群配置仍需对应的 `LARK_WEBHOOK_ENCRYPTION_KEY`。待同环境最后一个依赖迁移后再从运行配置移除。旧 `PORTAL_GA_STAGING_API_SECRET` 的生产使用需结合服务器脚本和配置核实。

### 退役账号操作密钥

本地 3000 已从 `.env.dev` 移除 `ACCESS_OPERATION_KEY`，其余配置及文件权限 `0600` 保持原样。重启后健康检查通过，前后端均运行 `d7abf9aab20f-bc907157ddbf1ee3`（提交 `d7abf9a`）。现有系统管理员登录与「系统管理 → 用户与权限」的用户、角色数据回读均返回 HTTP 200。未登录访问同一管理接口返回 HTTP 401。

Robert 在本地 3000 用现有管理员账号登录成功，并确认能分别打开「用户」和「角色」页面。自助改密和两位管理员互相重置密码沿用无旧密钥的模拟库验收。此次复验未改动现有账号的密码或权限。

公司测试先切换验收，生产在公司测试通过并获放行后按同样步骤执行。

1. 切换前，核对待确认的账号操作回执。按环境私下保留旧版本与旧启动配置供回退，在旧版本仍运行时保留其密钥。
2. 为 `d7abf9a` 或包含这项改动的后续版本准备启动配置。仅从新版本的私有环境文件和运行注入中删掉 `ACCESS_OPERATION_KEY`。如使用 `PORTAL_BOOTSTRAP_SECRET_FILE`，也要在新版本启动前清理该文件中的同名条目。新版会拒绝启动密钥文件中不在允许清单内的变量。仍有旧 Lark Webhook 密文时，保留其独立的 `LARK_WEBHOOK_ENCRYPTION_KEY`。
3. 在切换窗口用新配置启动新版。核对健康状态与前后端版本，用现有系统管理员重新登录，并进入「用户与权限」读取用户和角色。公司测试通过后再安排生产切换。
4. 如需回退到依赖旧变量的版本，用同一环境留存的旧配置和旧版本一起回退。回退完成后重新核对启动、登录与权限回读。

## 迁移旧 SMTP 和 Lark 群密文

使用已接入统一凭证读取的应用版本，以及同一环境的数据库、旧解密密钥和 `PORTAL_CREDENTIAL_KEYRING_FILE`。明确传入 `--environment dev|test|prod`。运行配置或密钥文件的环境与命令不一致时，工具在打开数据库前停止。先核对目标和可恢复备份，再默认运行只读预览。以下以本地为例。

```bash
node --import tsx scripts/migrate-legacy-integration-credentials.mts --environment dev
node --import tsx scripts/migrate-legacy-integration-credentials.mts --environment dev --apply
```

预览只输出数量。先核对每个集合的 `eligible`、`retainedManaged`、`retainedInactive` 和 `blocked`。旧 SMTP 用 `PORTAL_ENROLLMENT_MAIL_CREDENTIAL_KEY` 解密，旧 Lark Webhook 用 `LARK_WEBHOOK_ENCRYPTION_KEY` 解密。启用签名的群同时迁入原签名密钥，缺少签名密钥时计入 `blocked`。原配置实际由环境变量供给的群不会切换到数据库中的旧地址。现有托管和已撤销的凭证保持原状态。

执行使用本环境当前密钥版本重新加密，核对回解一致后写入并记录审计。没有供应商调用，不改变通知配置。已迁移项重复执行时归入 `retainedManaged`，无新增。若存在 `blocked` 项，它们保持旧状态，命令返回非零状态，其他合格项仍可成功迁移。执行后再预览，核对新增待迁移项为零。保留旧密文、旧密钥及独立备份，待运行读取和回退条件分别核对后再退役旧来源。

### 本地 3000 的 SMTP 旧密钥退役验收

本地开发库的 5 个 SMTP 账号在清理前后均逐一确认由后台托管，且使用 `PORTAL_CREDENTIAL_KEYRING_FILE` 成功解密。核对时令旧密钥不可用，确保凭证读取不依赖旧来源。确认回退材料已保存后，从本地账号配置清除 3 份旧格式密文，并从私有 `.env.dev` 移除 `PORTAL_ENROLLMENT_MAIL_CREDENTIAL_KEY`。

本地 3000 以原构建重启并通过健康检查，报名开放状态保持原样。重启后通过同一构建的投递逻辑执行一次模拟投递，确认回执为 `simulated` 且本地模拟文件可读取，随后清理本次测试记录。该验收未连接真实 SMTP。

如需回退，先确认本地发件配置和私有环境文件自本次变更后未被其他操作更新。如有后续变更，逐项核对后再恢复。使用本次 Git 忽略的私有回退副本（目录权限 `0700`，文件权限 `0600`）恢复原账号配置与修订号，以及私有 `.env.dev` 中的旧密钥，然后重启 3000。逐账号重新核对生效来源，并用模拟投递确认。切回依赖旧格式的版本前，须同时恢复对应旧密文和旧密钥。

**测试和生产在各自完成迁移、逐账号解密验收和回退确认前，继续保留本环境的 `PORTAL_ENROLLMENT_MAIL_CREDENTIAL_KEY` 及对应旧密文。** 本地结果仅适用于本地开发库，旧格式兼容仍保留。

### 本地 3000 的 OpenAI 和 DeepSeek 凭证迁移验收

本地开发环境逐家验证原有 API Key，使用 `PORTAL_CREDENTIAL_KEYRING_FILE` 对凭证加密，保存到各自的后台凭证槽位。重启后确认当前主备模型读取后台凭证，再从私有 `.env.dev` 移除该供应商的旧变量，重启并复验。主备模型选择保持原样。

| 角色和模型 | 移除的本地变量 | 重启后验收 |
|---|---|---|
| OpenAI 主模型 `gpt-6.2-sol` | `OPENAI_API_KEY` | 后台凭证解密及 JSON 回复、流式回复、结构化提取通过 |
| DeepSeek 备用模型 `deepseek-v4-pro` | `DEEPSEEK_API_KEY` | 后台凭证解密及 JSON 回复、流式回复、结构化提取通过 |

验收通过本地当前构建的模型探测逻辑，使用虚构输入分别调用两家供应商。备用模型独立验收，未注入主模型故障测试自动切换。

如需回退，先核对该供应商的后台凭证版本与本次迁入版本一致，并检查私有环境文件是否有后续修改。使用 Git 忽略的私有回退副本，仅恢复该供应商原有的环境变量和迁移前的凭证槽位状态。此轮迁移前两家均无后台槽位，回退时仅移除要回退的供应商本次新建的槽位。重启 3000 后核对凭证来源，并重新验证对应模型。逐家回退，保留另一家已验收的迁移。

**测试和生产继续保留各自的 `OPENAI_API_KEY` 和 `DEEPSEEK_API_KEY`，直到各环境逐家完成后台迁移、重启及调用验收。** 应用继续兼容旧变量。

## 轮换与恢复

1. 新增密钥版本并设为 `active`。各运行实例使用同一环境密钥版本集合。确认实例已读到新版本，并保留旧版本供读。使用只读挂载时重新加载挂载，确认读取的是更新后的文件。
2. 从与运行制品同版本的源码、使用批准的目标连接配置执行预览。计数中 `verified` 是已回读数量，`pending` 是本次需要重加密的数量，`rewrapped` 是实际重加密数量，预览始终为零。确认预览可解密所有记录，目标环境和备份已核对，再追加 `--apply`。只重加密该环境的活跃和候选凭证，保留凭证版本和操作记录。执行后再次预览，确认 `pending` 为零。

   ```bash
   node --import tsx scripts/rotate-integration-credentials.mts --environment dev
   node --import tsx scripts/rotate-integration-credentials.mts --environment dev --apply
   ```

3. 在批准的恢复演练中，以对应备份和密钥验证读取，再确认运行环境从密钥文件移除不再使用的旧版本。离线保存旧备份需要的历史密钥。回退到还未支持数据库凭证的制品前，逐个核对批准的旧来源和开关。已经撤销的凭证应在旧来源同步撤销或保持对应外发关闭。
4. 数据库恢复和恢复签名沿用管理员恢复流程。启动前核对备份与密钥版本配对，先只读验证解密、账号、需要处理的队列和发送状态。已送达及结果不确定的历史记录按原门禁处理。恢复实发需要单独批准。
