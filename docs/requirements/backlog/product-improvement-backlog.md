## UX-01：测评后的结果摘要与继续咨询

<a id="ux-01"></a>

- 状态：待确认；原优先级P1。
- 页面：客户侧`/chat`咨询页。
- 入口：首页或`/link`→免费在线咨询；已完成测评的用户再次进入，查看聊天区的测评报告。

### 问题与实例

回访用户进入咨询后，完整测评报告占用较长空间。继续咨询的输入区与下一步操作不够突出，用户可能需要滚动寻找。问题针对测评后的咨询体验，不涉及首页项目介绍。

### 建议动作

- [ ] 默认展示简短结果摘要，保留有实际结果支持的结论与必要提示。
- [ ] 提供清楚的“继续咨询”和“查看完整报告”入口。
- [ ] 完整报告按需展开，避免在同一聊天位置重复展示摘要和整份报告。
- [ ] 继续咨询时让输入区可见；展开／收起报告时保持阅读位置和输入草稿。

预期收益：减少重复阅读，缩短从看结果到询问课程或联系顾问的路径。

### 保留边界与待确认事项

- UX-04已将星级改为HSK 1／2／3答题表现；本项不恢复星级，不改变评分、定级和结果记录。
- 首次完成测评与回访用户是否采用相同默认展开状态，须确认。
- 摘要具体保留哪些结果、用户主动展开后的状态是否保留，须确认。

### 验收标准

- [ ] 已完成测评的用户能看到结果摘要及继续咨询入口。
- [ ] 完整报告可展开、收起，原结果与必要提示完整可查。
- [ ] 输入内容不因展开／收起而丢失，不被滚动或浮层遮挡。
- [ ] 无结果、未完成、继续已有测评三种情况不被误显示为已完成。
- [ ] 没有新增测评、客户登记、消息发送或通知事件。

## UX-02：WhatsApp跳转前的内容预览

<a id="ux-02"></a>

- 状态：待确认；原优先级P1。
- 页面：客户侧`/chat`咨询页。
- 入口：页头“联系真人顾问WhatsApp”按钮。

### 问题与实例

按钮会携带基本资料、学习需求及测评摘要打开WhatsApp。携带内容主要通过鼠标悬浮提示说明，用户在跳转前不容易看清具体文字。当前仍由用户在WhatsApp中手动发送，不能说成已经发送。

### 建议动作

- [ ] 跳转前展示将带入WhatsApp的实际消息预览。
- [ ] 允许编辑消息，或选择仅携带咨询文字。
- [ ] 用简短说明明确：“将在WhatsApp中打开，确认后由你发送。”
- [ ] 用户取消时回到原聊天位置，保留已有输入。

预期收益：让用户掌握携带信息的范围，减少意外带出资料和重复编辑。

### 保留边界与待确认事项

- 不自动发送WhatsApp消息；打开链接不等于已联系或已完成销售动作。
- 不带入CRM内部备注、AI内部判断、其他客户信息及无关历史。
- 预览默认携带哪些基本资料、结果和需求，以及“仅咨询文字”的具体内容，须确认。
- 不重新设计WhatsApp服务端集成，不自动创建任务或顾问请求。

### 验收标准

- [ ] 预览内容与最终链接携带文字一致。
- [ ] 编辑和“仅咨询文字”选择真正影响最终文字；取消不会跳转。
- [ ] 未测评、资料缺失时不携带虚构结果或空白字段。
- [ ] 中文、标点、换行和特殊字符正确编码，不因重复参数携带两份内容。
- [ ] 重复打开、返回聊天均不产生发送或联系完成记录。

## UX-05：此前约定与当前处理状态

<a id="ux-05"></a>

- 状态：暂缓；原优先级P1。
- 页面：CRM→客户详情→跟进页签。
- 入口：客户列表→匿名样例客户→跟进→客户约定区域。

### 问题与实例

匿名样例客户的阶段已是“已报名”，下方仍突出一条早于报名的约定。用户不容易区分这是此前约定，还是当前仍要追问报名的事项。

### 建议动作

- [ ] 将约定的原始内容、发生时间和当前处理状态分开表达。
- [ ] 对需要核对的旧约定明确显示“此前约定”，提供相应历史依据。
- [ ] 阶段变化后，如需提示，提示销售核对约定是否仍需处理；不代替销售作出完成判断。

预期收益：减少重复追问和错误跟进，同时保留真实历史。

### 保留边界与待确认事项

- “已报名”不能证明所有此前约定均已履行；不能按阶段自动完成、取消或删除约定。
- 既有有效约定、期限、提醒和取消机制保持原规则。
- 哪些场景需要核对提示、提示放在哪里、是否需要额外操作，均待确认；不能按原文关键词猜测约定已失效。

### 验收标准

- [ ] 已报名但仍有服务安排待处理的约定继续清晰可见。
- [ ] 报名前的历史约定不会被误读为重新要求确认报名。
- [ ] 原文、发生时间、原期限及历史处理记录完整保留。
- [ ] 仅浏览或改变展示不更新约定状态、不新增任务、不重新排期或发送通知。

## UX-07：准备联系中的客户上下文与联系目的

<a id="ux-07"></a>

- 状态：暂缓；原优先级P2。
- 页面：CRM→客户详情→准备联系抽屉。
- 入口：样例客户详情页头→“准备联系”。

### 问题与实例

为已报名的样例客户打开准备联系后，仍默认提供首次介绍式话术。问题是联系草稿没有充分体现已有沟通上下文，不是跟进记录的保存功能失效。

### 建议动作

- [ ] 提供明确联系目的，例如“回应本次问题”“继续已有沟通”“首次介绍”。
- [ ] 展示与本次联系有关的沟通摘要和依据，供销售参考。
- [ ] 销售选择目的后生成或准备相应草稿，已有沟通不再机械使用首次介绍。
- [ ] 客户语言尚未确认时，将草稿语言表达为建议语言，不冒充客户确认的偏好。

预期收益：减少销售重写话术，避免向熟悉客户发送陌生开场白。

### 保留边界与待确认事项

- 打开、生成、复制草稿或跳转WhatsApp，不等于已经联系。
- 不自动修改客户语言偏好、联系结果、销售阶段或任务状态。
- 联系目的选项、默认选择、引用上下文范围及是否调用AI，实施前须确认。
- 不覆盖销售正在编辑的草稿，不发送未经销售确认的文字。

### 验收标准

- [ ] 首次联系、继续沟通、回应具体问题分别得到符合目的的草稿。
- [ ] 已报名客户不会无条件落到首次介绍话术。
- [ ] 缺少上下文或语言偏好时明确表示未知，不编造客户承诺。
- [ ] 切换目的、后台刷新、关闭／返回均保留原草稿保护。
- [ ] 联系限制、客户权限、复制和跳转行为沿用原规则。

## UX-08：同一沟通事件的阅读去重

<a id="ux-08"></a>

- 状态：暂缓；原优先级P2。
- 页面：CRM→客户详情→跟进页签。
- 入口：样例客户详情→跟进→沟通动态与重要信息。

### 问题与实例

“有效沟通”和“客户互动”可能指向同一条WhatsApp记录，下方最新沟通结论又重复该次内容。销售需要多次阅读同一件事。

### 建议动作

- [ ] 保留既有三种时间线和统计定义。
- [ ] 阅读层按同一真实事件合并展示，标明该事件同时满足哪些业务口径。
- [ ] 同源内容共用一个依据入口，完整原文仍可查看。
- [ ] 联系结果、沟通结论与其他独立业务事实有不同信息时继续保留。

预期收益：减少阅读量，不损失业务事实或统计含义。

### 保留边界与待确认事项

- 合并须依据真实事件ID及来源关系，不能仅凭文字相似或发生时间接近。
- 不把打开页面、AI回复、客户消息和销售确认联系混为一件事。
- 不删除底层记录，不修改联系次数、客户互动统计和时间排序。
- 合并后的卡片结构、业务标签及展开内容待确认。

### 验收标准

- [ ] 同一真实沟通不在阅读流中重复出现多张相同摘要。
- [ ] 不同事件即使内容相同，也不会被错误合并。
- [ ] 可识别该事件所属口径，原时间、结果和依据均可查。
- [ ] 没有重复依据按钮，也没有因去重隐藏修正、冲突或不同原文。
- [ ] 合并前后业务计数及状态保持一致。

## UX-11：客户列表默认信息密度

<a id="ux-11"></a>

- 状态：暂缓；原优先级P2。
- 页面：CRM→销售线索→四列客户列表。
- 入口：销售管理→销售线索，重点为“互动与跟进”列。

### 问题与实例

三条时间线、阶段、需求、里程碑和多条“暂无记录”同时展示，单个客户行可能很高。销售不容易同屏比较客户、判断处理顺序。

### 建议动作

- [ ] 默认突出姓名及负责人、待处理事项、最近关键互动、阶段和核心需求。
- [ ] 完整三条时间线按客户行展开，或提供明确的详细视图。
- [ ] 减少重复的空状态说明；必须处理的事项及其期限仍直接可见。
- [ ] 使用信息取舍降低行高，不通过缩小字号或裁掉重要提示压缩空间。

预期收益：同屏比较更多客户，更快识别需要优先处理的客户。

### 保留边界与待确认事项

- 紧凑视图的具体默认字段、展开位置及详细视图方式须先确认样板。
- 保留筛选、排序、权限、匹配人数、选中位置和返回状态。
- 不改变“待处理”判定、任务期限、联系限制及现有统计定义。

### 验收标准

- [ ] 中文电脑端常见客户的默认行高明显减少，主要操作及待处理事项仍可见。
- [ ] 长姓名、多需求、逾期／未知状态和空记录不会造成整行布局失稳。
- [ ] 展开后能查看完整信息，返回详情和列表时保留原位置。
- [ ] 无权限操作继续隐藏，不能通过展开获得额外权限。
- [ ] 英语／印尼语及窄屏能力保留；实际测试范围另行按授权确认。

## UX-12：客户资料的属性值、来源与标题层级

<a id="ux-12"></a>

- 状态：暂缓；原优先级P2。
- 页面：CRM→客户详情→客户资料页签。
- 入口：样例客户详情→客户资料→基本资料、客户洞察／学习需求与偏好。

### 问题与实例

多个属性重复展示同一来源及精确到秒的时间；“客户洞察”下面再设“学习需求与偏好”，增加标题层级。属性值没有明显优先于来源信息。

### 建议动作

- [ ] 围绕基本资料、学习背景与需求、客户来源与分组组织内容，减少重复标题。
- [ ] 属性值为第一视觉层，来源和AI标识为第二层。
- [ ] 完整时间、采用理由和历史变化按需在依据详情中查看。
- [ ] 只有确实共享同一依据的属性才合并来源说明，并保持字段与依据关系清楚。

预期收益：销售先读到客户情况，需要核实时仍能快速查到来源。

### 保留边界与待确认事项

## UX-17：全局依据入口的紧凑统一设计

<a id="ux-17"></a>

- 新增日期：2026-11-06。
- 状态：已确认纳入待办；具体设计方案待确认，未启动产品修改。
- 建议优先级：P2；实际排期未确定。
- 页面范围：盘点全局现有依据与来源展示；重点覆盖CRM客户列表、客户资料、跟进动态、测评及客户全景，其他工作区存在同类入口时一并登记。
- 入口：具体属性值、沟通结论、测评结果、历史记录及补充／修正结果旁的“依据／来源”控件。

### 问题与用户目标

当前部分位置同时展示来源渠道（如客户问卷、客户对话）、日期、图标、“依据”文字和跳转箭头。辅助追溯信息占据较多空间，容易与真正需要阅读的内容争夺注意力。用户通常先关注信息本身，需要核实时才查看来源细节。

用户提出的方向：用单个、表意清楚的图标表示依据入口，紧挨具体信息；点击后再查看来源及详细内容，使页面更干净、紧凑，减少注意力分散。同一套入口允许按依据类别使用不同图标，例如区分客户直接填写的问卷答案与AI从客户对话中提取的信息。

### 建议动作

- [ ] 逐页盘点现有依据入口，区分来源渠道、来源日期、原文引用、AI整理标识、采用状态及业务时间，列出可收起的重复信息。
- [ ] 设计全局一致的依据入口及有限的图标变体；每处默认只展示一个图标，紧邻它所解释的信息，不再叠加来源名称、另一枚AI图标、“依据”文字和跳转箭头。
- [ ] 保持图标低强调但可识别、可点击；在长文本换行、表格和窄列中也能明确判断它属于哪项内容。
- [ ] 点击后显示对应来源类型、必要时间、原始答案或引文、采用说明及完整记录入口；延续已完成的字段精准定位，不让用户重新查找。
- [ ] 同一信息的共享依据只提供一个入口，并明确覆盖范围；不同依据不为节省空间错误合并。
- [ ] 复用共享控件和现有语义颜色，统一悬停、键盘焦点、加载、失败和不可用状态。

预期收益：减少重复标签和占位，提高列表及详情的信息密度，让销售先读信息、需要时再核实来源。实际节省空间和识别效率须以样板对比验证，不预先承诺量化提升。

### 图标按来源与处理方式区分

用户补充：单个入口可以因依据类别呈现不同图标。统一的是入口位置、交互和视觉语言，不要求所有来源使用完全相同的图形。以下为待设计的分类，具体图形和最终分类数量须通过样板确认。

| 依据类别 | 图标需要传达的含义 | 点击后需要说明 |
| --- | --- | --- |
| 客户问卷直接答案 | 客户直接填写的结构化回答，未经过AI语义提取 | 对应问题、原始答案、提交时间及当前值的采用关系 |
| 客户对话原文 | 客户实际说过的原话，作为直接引用查看 | 原消息、上下文和实际发生时间，不把系统摘要冒充原话 |
| AI从客户对话提取／整理 | 原始来源是客户对话，当前内容经过AI处理 | 原句及上下文、提取／整理结果、处理方式和采用情况 |
| 员工直接记录／人工更正 | 员工填写或明确修正的资料，有人工操作依据 | 操作者、原记录、变更说明、前后值和记录时间 |
| AI从员工记录提取／整理 | 原始来源是员工记录，当前内容经过AI处理 | 员工原文、AI结果和采用情况；与客户本人原话区分 |
| 系统实际业务记录 | 真实测评、报名、到账等业务流程产生的记录 | 对应业务记录和结果；不以AI陈述替代已完成事实 |
| 多份依据或来源未明 | 存在多个来源，或不足以确定单一类别 | 分列真实来源与处理方式；未知部分明确说明，不猜测类别 |

- [ ] 分别记录原始来源与处理方式，再按真实组合选择图标；不能把“AI”当作一种原始来源。
- [ ] 对AI处理内容评审统一的单图标变体，让用户能区别直接答案与AI整理；不在每个入口旁重新堆叠多枚图标。
- [ ] 对同属AI处理、但原始来源不同的情况，在有限变体和清晰提示之间取舍；不为每种组合无限增加图标。
- [ ] 每个变体都保留“查看依据”的可点击含义。悬停、键盘聚焦和无障碍名称说明具体类别，例如“查看学习目标的依据：客户对话，经AI整理”。
- [ ] 多来源时使用统一的多依据入口，点击后分列来源；不能只挑问卷或AI其中一类代表全部依据。

### 保留边界与待确认事项

- 图标化的是辅助追溯入口，不是一律隐藏所有日期。沟通实际发生时间、约定到期时间、逾期或异常提示等独立业务信息须按其用途保留。
- 来源渠道、AI处理方式和采用状态含义不同。是否简化AI标识及状态展示应逐项评审，不能把AI整理冒充客户原始陈述，或把冲突隐藏进普通图标。
- “问卷直接答案”只说明采集方式明确，不代表答案经过事实核验、永远有效或已经被当前资料采用。图标不承担真实性评分或采用状态判断，也不使用勾选、认证等图形误导用户。
- 无真实依据时不提供假入口；无权限查看的依据不因统一图标获得额外访问权限。来源缺失、撤回和修正等必要提示保留。
- 图标候选、是否需要简短提示、点击后采用就地展开还是已有全景定位、不同上下文的统一行为，均须先做设计样板并确认。
- 图标不能只靠用户猜测：提供明确的无障碍名称，例如“查看课程总预算的依据”；悬停和键盘聚焦可显示简短说明，详情查看不依赖悬停。
- 与UX-08、UX-12及UX-14C有交集。统一设计并关联验收，不自动解除这些条目的暂缓状态，也不重复实现UX-09、UX-15已经完成的依据能力。
- 保留完整原文、日期、来源关系和历史依据，不更改底层数据、权限、采用规则或通知行为。

### 验收标准

<a id="br-05"></a>

- 状态：已纳入Backlog，具体方案待确认；建议P1，工作量小到中，内容需公司核定。
- 页面／入口：公开网站页脚，以及联系、问卷、转人工等资料采集节点。
- 问题实例：当前隐私政策与服务条款为占位链接，资料采集用途与AI处理说明需逐入口核对。
- 预期收益：改善用户信任和告知体验。

建议动作与待确认：

- [ ] 由公司核定真实说明内容、适用范围、沟通渠道及联系途径；必要时交专业人员核对。
- [ ] 建立有效页面，并在采集节点提供短说明及详情入口。
- [ ] 说明与真实处理方式保持一致，不用虚构条款或形式勾选替代告知。

验收：链接可访问，打开／返回不丢草稿，说明与实际处理一致。此项不等于法律合规认证；不擅自接受或代用户签署条款。

## BR-06：同批次营销经营分析

<a id="br-06"></a>

- 状态：已纳入Backlog，具体方案待确认；建议P1，工作量中到大。
- 页面／入口：活动中心→结果与客户／推广链接；GA获取及漏斗报表。
- 问题：已有累计登记、测评、报名和净收款；不同投放周期、成本及观察期下的经营效果尚不易比较。
- 预期收益：支持渠道选择与预算分配，减少误读累计比例。

建议动作与待确认：

- [ ] 明确登记周／月分组、观察期、有效咨询定义和样本范围；未满观察期另列。
- [ ] 实际投放支出与计划预算分开，先评估可追溯的人工录入／导入，再决定是否接广告平台。
- [ ] 有可核验分母后再计算有效客户成本、报名成本；区分首次来源、本次访问和再次购买来源。

验收：可按相同观察期比较业务产出；无数据时不可计算，不将点击当客户、报名当到账、计划预算当实际成本或净收款当利润。统计留在活动中心，CRM与GA口径分开解释。

## BR-07：合同变更与终止结算

<a id="br-07"></a>

- 状态：已纳入Backlog，完整业务及权限方案待确认；建议P1条件项，工作量中到大。
- 页面／入口：客户→报名与收款；收款核验→项目详情。
- 问题实例：合同应收200万、到账200万、退款50万时，合同不变则剩余应收50万有其计算逻辑；若因终止课程退款，还需独立说明终止后的应收／应退，不能只看该余额。
- 预期收益：避免错误催收、错误退款和账款语境混淆；真实退课／合同变更出现前须优先评估。

建议动作与待确认：

- [ ] 分开记录原合同应收、获批商业调整、到账、退款及终止结算，明确未收款和未履约的区别。
- [ ] 确认商业调整／结算权限、实际服务依据及保存事务，不把财务核验当成优惠改价。
- [ ] 保留逐笔事实与历史，不靠改阶段、作废真实付款或猜测已履约课时结算；不扩大成完整会计／教务系统。

验收：覆盖分期、全额后部分退款、退课未退款、未收款终止及退款后误记作废；金额、结算和真实款项一致，退款不得超过可退实际收款。含GA上报的口径若需变化，另行明确并在安全方式下验证。

## BR-08：轻量机会与再次购买

<a id="br-08"></a>

- 状态：已纳入Backlog，实施细节待确认；建议P1条件项，工作量中到大。
- 页面／入口：客户详情→阶段与报名；课程统计及客户长期关系。
- 问题：当前主线限制一个首次报名项目，客户再次购买新课程需要独立销售过程，不能覆盖原成交或重复建客户。
- 预期收益：支持复购，保留多次成交与款项历史；真实再次购买出现前须评估完成。

建议动作与待确认：

- [ ] 详细需求以[CRM轻量销售机会](crm-lightweight-sales-opportunities.md)为准，本条只登记评审优先级和关联，不复制第二套规则。
- [ ] 保持一个客户档案，每次购买有独立销售过程和报名项目；明确首次自动创建与复购人工确认的边界。
- [ ] 不由一般咨询／AI兴趣自动创建机会，不建设三套客户工作区或额外负责人体系。

验收：同一客户两次购买、第二次未成交、分项目退款及来源均清楚；原资料、报价、付款、负责人及期限按确认方案保留。

## BR-09：跨页面一致的AI派生理解

<a id="br-09"></a>

- 状态：已纳入Backlog，架构与展示方案待确认；建议P2，工作量中。
- 页面／入口：客户列表提示、资料学习目标、跟进重要信息及历史依据。
- 问题实例：UX-06已在资料页把目标表达归为补充，列表仍显示“另有表述”提示；只读复核由浏览发起，短时缓存，等待、重复费用及长期一致性需评估。
- 预期收益：减少重复核对、等待和模型请求。

建议动作与待确认：

- [ ] 按原始依据、字段版本和模型／规则版本复用派生比较结果，评估异步更新及失效机制。
- [ ] 列表、资料及跟进引用同一有效结论；未知／失败保守表达，给出明确恢复方式。
- [ ] 不改当前采用值、不重跑旧队列或重写历史，不用关键词替代语义；保持权限和并发保护。

验收：同客户跨页面含义一致，新版本不沿用旧结论；测量请求次数、等待与失败恢复。现阶段只记录代码可见风险，不声称已发生模型结论反复变化。

## BR-10：分层信息与紧凑依据样板

<a id="br-10"></a>

- 状态：已纳入Backlog，关联汇总／方案待确认；建议P2，工作量中，不单独建立重复实施范围。
- 页面／入口：列表、资料、跟进、测评和客户全景的属性与依据。
- 问题：来源、日期、AI标识、依据文字及箭头容易与信息本身争夺空间。
- 预期收益：提高可扫描性，减少阅读噪声。

建议动作与待确认：

- [ ] 图标分类、来源／处理方式及交互要求统一维护于[UX-17](#ux-17)，实施和验收证据相互引用。
- [ ] 以列表摘要、当前情况、完整依据的不同阅读任务设计样板，优先统一信息层级和对齐。
- [ ] 保留关键业务时间、冲突、撤回和无障碍信息；复用已完成的UX-09、15，不重做定位能力。

验收：用户能识别图标并快速找到特定信息依据；小图标有足够点击区域和键盘支持。UX-12、14C仍暂缓；UX-10的拒绝决定不变，不改默认双侧全景。

## BR-11：通知阅读与业务处理分层

<a id="br-11"></a>

- 状态：已纳入Backlog，具体方案待确认；建议P2，工作量中。
- 页面／入口：通知铃铛侧栏、个人通知设置、通知策略及发送记录。
- 问题：信息动态、业务提醒及已读状态混排；“读过”不能说明任务或约定已处理。旧依据不可用的通知也需清晰表达。
- 预期收益：减少无效阅读，帮助找到真正需要处理的事项。

建议动作与待确认：

- [ ] 设计“需要处理／全部消息”或等效分层，业务状态来自原事项，不来自已读标记。
- [ ] 同事项多次提醒在阅读层聚合；保留完整发送历史，不静默删除或合并不同事项。
- [ ] 处理已结束事项的强调方式和不可定位的旧消息；不猜测跳到其他记录。

验收：未处理事项可定位，已读与完成不混用，权限及既有排期、去重、必收提醒和Lark发送规则不变。以处理时长及漏办验证，不把测试未读数当真实业务表现。

## BR-12：轻量CMS运营发布流程

<a id="br-12"></a>

- 状态：已纳入Backlog，范围与权限方案待确认；建议P2，工作量中。
- 页面／入口：CMS→编辑／保存生效，官网各语言动态内容。
- 问题：已有编辑与保存保护，但保存即生效、语言版本、内容复核与责任较薄；当前分类总数说明也有遗留。
- 预期收益：减少误发布、过期内容和多语维护返工。

建议动作与待确认：

- [ ] 评估草稿、按语言页面预览、明确发布动作及最近复核时间，先治理价格／日期等高影响内容。
- [ ] 明确内容负责人、过期检查与图片替换流程；多人协作确有需要时再拆编辑／发布权限。
- [ ] 营销文案建立语言版本或明确回退，真实评价及原文保持；商业字段与BR-01共同设计。

验收：样例不会误上线，保存草稿与发布含义清楚，可核对页面与素材，原保存结果／并发／权限保护不退化。未批准前不迁移现有内容或修改发布状态。

## BR-13：自动化异常的责任兜底

<a id="br-13"></a>

- 状态：已纳入Backlog，运营规则及页面方案待确认；建议P2，工作量小到中。
- 页面／入口：自动分案、历史补分、身份／来源核实、员工停用及转交。
- 问题：轮询和补分保护已存在，但无可用销售、未分配、待核实及人员交接的例外需要明确责任。
- 预期收益：减少无主客户与异常积压，让经理快速定位处理原因。

建议动作与待确认：

- [ ] 明确“为何未分配、谁处理、原首次期限是否已到”及可用的现有操作入口。
- [ ] 规定员工停用交接、无人接待兜底及身份／来源异常的责任，保留不同核实边界。
- [ ] 先用积压与接待能力评估现有轮询，再决定加权／条件／值班策略，不新增无用配置。

验收：异常可解释、可分工，不刷新原期限、不越权转交、不重复分案、不制造意外通知。所有真实客户归属变更须按后续实施授权执行。

## BR-14：真实角色任务验收与单一现行口径

<a id="br-14"></a>

- 状态：已纳入Backlog，落实范围待确认；建议P2，持续运营工作。
- 页面／入口：全工作区，系统管理→角色／权限预览／审计，在线帮助和运营指南。
- 问题实例：已有规范，但裸`/link`来源的新旧文档有不同说法；多角色管理账号的检查不能代替普通销售、财务和内容人员的使用体验。
- 预期收益：减少口径漂移、培训成本、权限困惑及局部返工。

建议动作与待确认：

- [ ] 为关键规则指定唯一现行说明，核对产品、初始化值、在线帮助及验收场景；旧文档标历史或改为入口链接。
- [ ] 定义营销生成入口、销售处理事项、财务核款、内容发布、管理员交接权限的代表任务。
- [ ] 先确认业务层级与样板，再复用组件推广；获授权后开展角色任务观察，记录完成率、耗时及误解。

验收：现行说明无相互矛盾；任务完成与角色权限、保存恢复、草稿保护一致。不得把组件存在或自动测试通过冒充真实效率验证；不自动变更角色、生产数据或既定业务规则。
