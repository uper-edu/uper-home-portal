# AI Chat 招生咨询评测

这套评测判断 AI 能否把咨询办完。咨询阶段包括解释、核对、比较和找到可执行的下一步。申请和交易由学员在 Enrollment 操作。退款审批、银行核款、非公开报价和具体预约由有权限的人员完成。

## 平时怎样跑

1. 默认运行 `node --import tsx scripts/evaluate-chat-consultation.mts`。使用固定数据跑自动断言，覆盖当前报价、节与次、分日排课、满班、无匹配、暂停和链接。
2. 模型、提示词、会话上下文、事实读取改变后，在本地 3000 加载待验收版本。沿用现有本地模拟邮件和发送保护。用 `/api/version` 核对前后端构建一致。
3. 明确执行真实模型运行。命令如下。脚本只连接本地 3000，传入虚构资料，并在每个场景后清理该次专用的会话记录。题库中两例含虚构测评资料。链接只发同源 GET，停在提交前。
4. 两个放行阻塞用例独立复测三次，另存结果。`--cases=10,12 --repeat=3` 可指定。
5. 用评分命令校验公开记录与动作，再由两名评审盲评。评审隐藏模型、版本和答案来源，人工参考答复与 AI 使用同一份事实。开发中可检查公开题，留出题由运营维护，避免用其逐条调提示词。

```sh
node --import tsx scripts/evaluate-chat-consultation.mts --live --build=具体构建号 --output /private/tmp/chat-review
node --import tsx scripts/score-chat-consultation.mts /private/tmp/chat-review
node --import tsx scripts/score-chat-consultation.mts /private/tmp/chat-review /private/tmp/completed-reviews.json
```

核对咨询和点击是否误创建业务记录时，加 `--audit-verified-links`。评测使用独有的本地模拟身份，在对话前后读取已验证邮箱的订单列表及关联记录。对比商机、潜在占席订单、转班留位、候补、需求和客户关联。浏览目标页面和读取订单列表都使用 GET，核对结束后删除专用会话。评分输出 `enrollmentAudits`，老报告中未启用此项的用例不计入该覆盖数。

浏览器须分别验证独立聊天和首页浮窗。独立聊天首次显示登记邀请，可选择「先咨询」，随后仍可打开原资料表。核对跳过时没有注册请求、当前会话刷新保留选择、输入焦点和班次直达。

默认中文桌面和一条夹用 beginner 的对话。英文、印尼文未来分别建基线。固定数据模拟满班等难复现状态，真实结果须标注当地目录是否有样本。浏览器补验独立 Chat、首页浮窗和关键落地页，阻止 GA 与非本机外发。只保留脱敏结果于评审目录，运行记录、数据库和私有配置留在 Git 之外。

## 自动回归闭环

原 39 题继续沿用原口径。`--with-regressions` 追加两道自由追问 F2、F3，第 01 题仍使用原题。自动门禁逐轮核对原班次对、重复转账、咨询对象切换。题库和测试依据在 [回归题与门禁](../../tests/fixtures/chat-consultation-regressions.json) 中维护。

### 两个构建对照

在本地 3000 加载要测的版本。每次用相同模型、推理强度和题单。对照已有证据时可直接运行如下命令。

```sh
node --import tsx scripts/run-chat-consultation-loop.mts \
  --baseline /private/tmp/chat-before --candidate /private/tmp/chat-after \
  --output /private/tmp/chat-comparison
```

录制证据用 `evaluate-chat-consultation.mts --live --build=确切构建号 --model=gpt-6.2-sol --cases=01,F2,F3 --repeat=2 --audit-verified-links --output 路径`。分别放在两个目录。每组用独立的模拟身份，对话后核对订单、席位和商机等记录。

对照核验题单指纹、WIB 自然日、配置与回执模型、公开目录和报名状态。结果 `loop.json` 记录失败层级及证据，包括意图识别、条件保存、事实匹配、正文合成、链接和运行失败。报告会区分重复运行的结果。报价、时间和余位事实从同轮目录核对。

### 自动生成并复验候选

```sh
node --import tsx scripts/run-chat-consultation-loop.mts \
  --baseline-build 旧构建号 --model gpt-6.2-sol --cases 01,F2,F3 --repeat 2 \
  --worker scripts/chat-consultation-codex-worker.mjs --output /private/tmp/chat-loop
```

先配置受信任的本地候选加载程序。将绝对路径提供给 `UPER_CHAT_EVAL_LOCAL_LOADER`，并用 `UPER_CHAT_EVAL_BASELINE_SOURCE` 指向基线构建对应的源码。受信任工具通过标准输入接收 `load_candidate` 对象，含 `baselineBuild`、`baseCommit`、`source`、`patch` 和 `touched`。加载程序核对基线、建立候选并在同一个本地 3000 加载，成功后在标准输出返回 `{"kind":"build","buildId":"候选构建号"}`。本地工具需遵循仓库的模拟验证和数据保护要求。

候选生成器把咨询源码和模拟失败证据交给本机 Codex CLI。它先检查补丁涉及的文件和可应用性，再交给加载程序。评测程序按回读的确切构建号自动复验。评分工具和题库在候选可编辑范围之外。已有候选可使用相同的加载协议。

候选构建、测试或门禁失败时，流程先恢复本轮基线，再把失败的答复、断言或构建诊断与上一版补丁交给同一生成器。最多再生成一次，第二次仍未通过则恢复基线并结束。加载程序收到 `{"kind":"restore_baseline","build":"基线构建号"}` 后应恢复运行版本及本轮候选涉及的源文件，读取本地服务版本后返回 `{"kind":"restored","buildId":"基线构建号"}`。恢复未确认时流程报告 `restore_failed`，保留失败证据。测试条件不一致时恢复基线并报告不可比较。

遇到业务歧义时，`loop.json` 保留问题、基线指纹和运行参数，流程退出码为 3。答复后用原输出目录继续。

```sh
node --import tsx scripts/run-chat-consultation-loop.mts \
  --output /private/tmp/chat-loop --resume --answer '已确认的业务口径'
```

`targeted_pass` 表示选中的门禁通过，`incomparable` 表示基线和候选的测试条件不一致，`rejected` 表示候选仍有失败或质量退化。

完整质量比较可读取两份已有评审，或加 `--judge scripts/chat-consultation-codex-judge.mjs`。评审程序分别从学员和招生运营视角打分，有分歧时根据原文补做复核。输入省去构建和被测模型标识。保留分项分数、原始评审和复核理由，模型评审用于本地比较。自定义评审程序从标准输入接收 `grade` 请求，内含题目、预期、答复和公开事实，输出与评审模板同结构的数组。`quality_pass` 需要完整题单的质量证据。定向检查优先用 `--cases`，完整题单评分用 `--repeat 1`。基线和候选使用相同评审程序和配置。

## 评分怎么算

| 维度 | 1 分 | 3 分 | 5 分 |
|---|---|---|---|
| 礼貌、清晰、上下文、准确、主动帮助 | 误解核心要求、误导或阻断 | 解决一部分，需要用户追问 | 直接准确，回应顾虑，提供必要帮助 |
| 需求识别、匹配、下一步、转化质量 | 导去无关入口或误触业务状态 | 能到达下一步，仍需重复说明或重新筛选 | 学员已了解适合的选择，可自主完成下一步 |

运行后生成 `review-template.json`。每个 `reviewerA` / `reviewerB` 填 `resolved`、`severe`、可定位证据的 `evidence`、`cause` 和 `scores`。学员评分键为 `courtesy clarity context accuracy initiative`，经营键为 `need match nextStep conversionQuality`。解决结果或严重性有分歧，或者单项差至少两分，在 `adjudication` 记录复核依据及结论。保存两份原评分，审核后再填写复核。

全量独立解决率含必须人工处理的用例。可独立任务解决率只使用运行前定义的可独立任务作分母。另用 `cause` 记录知识缺口、需要人工审批、错误转接、应该转接但未转接、模型理解、匹配或呈现。逐场记录轮次，核心问题解决且下一步匹配才算解决。浏览入口无需提交。给出可靠的无匹配结论和合适的需求登记也可以算解决。

人工接手单列三项。逐轮比较对话当时已知的事实和当前权限，记下不必要转人工、应转却没给到可达入口，以及合适转接中有多少保留已知课程条件并说明待顾问核实事项。07、23 看线下供给和主动找真人，10、16 看具体一对一排期，33 看本人订单入口与审批职责的边界。真人预约、退款结果与对话内给到下一步分别判定。

### 正文首答复验

用 `--cases=01,02,04,05,11,26,27` 跑固定的七道首答题。评审先只读 `reply`，逐轮记录是否答齐当轮问题，再打开卡片和入口检查补充信息。把通过轮次除以 7，单独报告这个比率。事实错误、只给通用提示，以及依靠追问才补齐，都按该轮未通过统计。

| 用例 | 正文须回答 |
|---|---|
| 01.3 | 第一班总节数、实际学费和申请步骤 |
| 02.4 | 从零开始的课程起点和接下来能做什么 |
| 04.4 | 恢复周五可用后，原班两天的准确开课与结束时间 |
| 05.3 | 预算内可完成整级的班型和推荐依据 |
| 11.1 | 指定班次的周五和周六时间，以及是否符合可上课时段 |
| 26.3 | 报价按一节计费，并解释它与两节组成的一次课的关系 |
| 27.2 | 聊天无法锁位，指出获席前需要学员完成的操作 |

用 `--cases=05,26` 定向复验计价与约课。26.3 的正文只需解释单位。对照 05.1 和 05.2，学员同时问金额时须列出实际价、标准价和每节价，同时问一对一报名时须说明由顾问约课，入口打开对应的一对一页面。

实收核验、取消后补交凭证和退款另看 19–22、33。正文须给出当前可执行的安全步骤，学员未验证邮箱时只解释通用规则和查单流程。案例 21 须明确请勿重复转账及如何查询原单，案例 33 须先交代退款获批条件。

逐轮核对回复是否随问题变化。12.3 明确只索要链接，正文只需指向仍开放的需求表。20.3 和 33.3 仅询问查询位置，直接给「我的报名」和验证步骤。28.3 的级别已有明确表达，指示填写「其他」及备注。01、05、32 的多班推荐可合并相同课表和学费，首课与其他差异仍标清对应班次。

## 放行

固定数据关键断言全部通过。真实模型运行零严重错误。错误报价、错报课表、虚构余位、否认可用的明确入口、测评当认证、未确认声称报名完成和误写交易均是严重错误。候选版本的可独立任务解决率至少 90%，学员与经营均分至少 4.0，两侧各基础场景至少 3.0。人工评审和三次独立复测都要有证据。下一阶段按最大可避免转接来源提高到 95%。100% 是咨询覆盖方向，需另行授权后通过真实客流核对重复咨询和人工接手，点击不计作成交。
