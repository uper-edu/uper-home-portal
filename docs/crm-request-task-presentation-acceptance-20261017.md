# 请求关联任务与跟进入口验收

日期：2026-10-17。独立服务：4426；独立 MySQL、模拟客户。本轮未切换 3000、未推送 GitHub、未部署服务器。

## 最终展示

- 顶部保留“当前关联跟进”，当前会话中每个 taskId 仅展示一张任务卡片：已保存动作、处理截止时间及运营时区、当前状态、负责人。
- “记录跟进”图标和文字统一放在每项右侧；390px 窄屏换行后仍居右。客户消息下不再重复操作按钮。
- 消息流直接区分“已创建跟进任务”“已补充到现有任务”，附可键盘操作的任务引用，定位顶部同一任务。
- 只依据新请求保存的 `metadata.taskOperation`，或足够明确的已保存来源标识判断新建／补充。旧记录证据不足时使用“关联跟进任务”；不从当前状态或时间猜测历史。
- 原始确认消息集中保留在底部“请求确认原文”，无嵌套折叠，原文和记录时间不改写。客户与 AI 消息原文保持不变。
- 处理截止时间不是预约时间，不显示“预约已确认”或“报名已完成”等未经证实的业务结果。

## 行为与权限

“记录跟进”沿用现有客户写入权限和结果表单。从未完成任务进入，只预选该任务；从已完成任务进入，不预选完成项，不重新打开旧任务。只有保存并明确勾选才会完成任务，打开／取消表单不改变任务状态。

原话关联按已保存的 conversation_id 和 request_id 寻找客户消息，不按相邻位置猜测。来源不足时仍可处理该任务，但不伪造客户原话关联。没有任务的信息仍可通过 Follow-up 的普通记录／随手记录入口保存。

新增 `taskOperation` 是新请求的元信息，不改变任务创建、同类去重、期限、Owner 路由或通知条件，也不批量回填历史消息。相同请求 ID 重试保持原操作结果；登记前请求后来完成身份关联时同步保存该操作证据。

## 数据保护与限制

- 验收前已有客户、消息、会话、员工、任务、测评、运营和通知配置的受保护记录哈希保持不变；打开表单及取消没有保存联系或完成任务。
- `.env.dev` 和 `build/dev/.uper-release.json` 哈希保持不变；本轮未访问 3000 业务数据库、未重启 3000。
- 通知 worker 关闭，通知为模拟模式；没有真实 Lark 发送或历史通知重放。本轮展示验收未新增真实 AI 调用。
- 浏览器操作角色为模拟 Sales；只读及越权边界还由自动化验证，未声称真实销售参与或完整系统无障碍认证。
- 旧来源不足时只能显示“关联”，不会补造新建／合并事实。多会话仍按当前选择分别查看；同一任务在每个选定会话内仅展示一张完整卡片。
- 私有截图、九组布局数据、哈希核对与测试日志位于 `.local-backups/crm-request-task-cards-20261017/`，不纳入 Git。
