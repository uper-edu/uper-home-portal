# 数据库增量 SQL 目录

本目录统一管理**可分发、需人工执行**的数据库增量 SQL。适用于同事本地库、测试环境和生产环境的增量发布；无论是人还是 AI，新增数据库增量时都必须遵守本规范。

## 命名规范

```
v<YYYYMMDDHHMMSS>_<简短用途>.sql
```

- 版本号 = `v` + **创建时刻的时间戳**（本地时间，精确到秒），例如 `v20261106115022_cms_cos_incremental.sql`。
- **禁止**使用 `v1`、`v2`、`…v20` 这类连续小数字：多人并行开发时会互相占用编号造成冲突。时间戳天然唯一且可读出创建时间。
- 时间戳取文件创建时的当前时刻，不要复用已存在文件的时间戳，也不要事后修改已发布文件的时间戳。
- 文件名只允许小写字母、数字和下划线；用途段用英文短词，能看懂这个增量做什么。

### `95eea57` → v20 批次：前置版本、执行顺序与回退

前置版本：目标库为 `95eea57` 对应的 v18，版本 1–18 均为 `ready`，无恢复屏障。三份 SQL 适用于公司 test 和 prod 的已有业务库，各环境分别授权、分别执行；不适用于空库。

执行顺序（回滚 SQL 不在此列，只在放弃升级时单独执行）：① `v20261126182423_portal_v18_to_v20.sql`（结构）→ ② `v20261126182717_reviewed_delivery_state.sql`（投递方式）→ ③ `v20261126192807_system_default_seeds.sql`（系统预设）。②、③ 都要求 ① 已完成，彼此无先后依赖。三份全部成功并复核后，新版应用的只读启动检查才会通过。

回退方式（回滚 SQL 和旧版迁移程序的兼容性已演练，见[执行手册](../docs/operations/manual-database-startup.md#6-回退)；备份恢复未演练）：

- **新版应用尚未使用新表时**，执行 `v20261127101113_rollback_v20_to_v18.sql`，一次撤销 ①②③，库回到 v18。它依据 ②、③ 写入的审计记录判断要撤销什么，适用于升级完成后放弃，也适用于升级中途失败。
- 该回滚不恢复 `social-bio` 的 `updatedAt`；升级和回滚各自的审计记录保留。系统飞书群名称恢复为 `95eea57` 的默认名「CRM Lark Bot」。若第 ② 份曾把群渠道改为模拟（审计中 `simulatedGroupCount` 大于 0），回滚会拒绝，须先按执行前记录恢复这些群的模式。
- **新版应用已写入新表后**（报名、收款分析、托管凭证等），回滚 SQL 会拒绝执行，因为删表会丢业务数据。此时只能保留数据库、切回旧制品，或从备份恢复并补录其后的业务。演练中 `95eea57` 的启动迁移程序在升级后的库上正常完成；旧版应用的页面和队列行为未实测。
- 切回旧制品后，旧版启动会为 4 个 `enroll-*` 预设生成短链；回滚 SQL 会一并删除这些短链。未执行回滚而再次升级前，须手工删除。

详见[手工数据库升级与启动门禁](../docs/operations/manual-database-startup.md)。

## 编写与发布要求（人与 AI 相同）

1. **先查 `trial_schema_versions` 与实际结构，再写增量**：不得只看最大版本号；增量需自带结构门禁，已应用的目标重复执行必须是数据零变更。
2. **不破坏既有数据**：默认保留目标库自己的业务内容、账号、权限和运行数据；破坏性操作（清空、删列、覆盖他人内容）必须在 README 登记行和 SQL 头部显式声明，并单独取得授权。
3. **禁止外键**：增量 SQL 不得新增 `FOREIGN KEY`/`REFERENCES`/级联子句，与 `AGENTS.md` 数据库规范一致。
4. **可移植**：不硬编码 IP、库名、账号、密码或某次私有备份；连接信息由执行者自己提供。
5. **遇错即停**：SQL 必须自带校验与明确的错误信号；文档中写明允许的执行客户端与终止行为。
6. **发布流程**：直接在 `main` 开发或经功能分支开发均可（用户 2026-11-06 确认两种方式并行允许；较大或多端并行的改动建议功能分支隔离）。推送前跑 `npm test`、`npm run lint`、`npm run build`、`git diff --check`；生产执行仍需单独确认与备份。
