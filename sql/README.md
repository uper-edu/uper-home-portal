# 数据库增量 SQL 目录

本目录统一管理**可分发、需人工执行**的数据库增量 SQL。适用于同事本地库、测试环境和生产环境的增量发布；无论是人还是 AI，新增数据库增量时都必须遵守本规范。

## 命名规范

```
v<YYYYMMDDHHMMSS>_<简短用途>.sql
```

- 版本号 = `v` + **创建时刻的时间戳**（本地时间，精确到秒），例如 `v20261106115022_cms_cos_incremental.sql`。
- **禁止**使用 `v1`、`v2`、`…v20` 这类连续小数字：多人并行开发时会互相占用编号造成冲突。时间戳天然唯一且可读出创建时间。
- 时间戳取文件创建时的当前时刻，不要复用已存在文件的时间戳，也不要事后修改已发布文件的时间戳。
- 文件名只允许小写字母、数字和下划线；用途段用英文短词，能看懂这个增量做什么。

## 每个文件必须登记到下表

新增、移动或废弃增量 SQL 时，**同一次提交**内更新本 README 的登记表和必要说明，保证目录自解释：

| 文件 | 创建时间 | 目标结构 | 作用 | 执行方式 | 验证 |
|---|---|---|---|---|---|
| `v20261105220918_cms_cos_incremental.sql` | 2026-11-05 22:09 | COS v16（含于 v18 体系） | 已有库对象存储改造：补 COS 字段/索引，写入 208 张正式媒体真实 COS URL，定向替换 CMS 图片引用；保留业务内容、账号与原 BLOB，可重复执行 | 新 mysql 进程 stdin 重定向整文件执行，禁 `--force`，详见 [docs/operations/cms-cos-incremental.md](../docs/operations/cms-cos-incremental.md) | 幂等零变更、9 个原生场景与 17 项回归，见该文档 |

## 编写与发布要求（人与 AI 相同）

1. **先查 `trial_schema_versions` 与实际结构，再写增量**：不得只看最大版本号；增量需自带结构门禁，已应用的目标重复执行必须是数据零变更。
2. **不破坏既有数据**：默认保留目标库自己的业务内容、账号、权限和运行数据；破坏性操作（清空、删列、覆盖他人内容）必须在 README 登记行和 SQL 头部显式声明，并单独取得授权。
3. **禁止外键**：增量 SQL 不得新增 `FOREIGN KEY`/`REFERENCES`/级联子句，与 `AGENTS.md` 数据库规范一致。
4. **可移植**：不硬编码 IP、库名、账号、密码或某次私有备份；连接信息由执行者自己提供。
5. **遇错即停**：SQL 必须自带校验与明确的错误信号；文档中写明允许的执行客户端与终止行为。
6. **发布流程不变**：改动在功能分支完成，跑 `npm test`、`npm run lint`、`npm run build`、`git diff --check`，审查后合并 `main`；生产执行仍需单独确认与备份。

## 与其他 SQL 的关系

- 应用启动自动迁移链（`cloud/mysql/schema*.sql` 与 `cloud/mysql/migrate.mjs`、`trial_schema_versions` 记录）由代码运行时管理，**不放入本目录**，也不要为它手工补编号。
- 仓库 CMS 正式种子与图片在 `cloud/mysql/seeds/cms/v2/`，是内容数据源，不是增量脚本。
- 完整空库初始化见 [docs/operations/cms-cos-bootstrap.md](../docs/operations/cms-cos-bootstrap.md)；不要把初始化包当增量导入已有业务库。
